# 全体監査 + TOP高速化 + DB最適化 実施レポート（2026-07-12）

> ユーザー要望「全体を精査（動作性・安定性・堅牢性重点）。特に TOP が重いのでフロント/バック精査、可能なら DB 最適化も」を受けた 3 領域（フロント / バックエンド / DB・RLS）並列精査と、確定約 20 件の修正実装。
> ブランチ: `claude/site-performance-stability-audit-fcobyi`（バッチ単位 4 コミット）。
> 過去の見送り確定（B-1 motion / B-2 optimizePackageImports / ISR / @supabase/ssr 剥がし / tailwind-merge / base-ui dynamic 化 / close transition）は判定を尊重し対象外。

## TOP が重かった構造要因と対処（バッチ A）

| # | 発見 | 対処 |
|---|---|---|
| A-1 | character-sheets 外部 fetch にタイムアウト無し — cold cache / `updateTag` 直後の同期再取得で外部遅延が TOP 全体を無制限ブロック（Data Cache は SWR のため通常経路は非ブロッキング、Next 16 実 docs で確認） | `AbortSignal.timeout(8s)` + 既存 fetch-failed カードへ degrade（`next-session.ts`） |
| A-2 | app_settings が同一リクエストで 3〜4 本の別 SELECT + `getScheduleSourceUrl()` の単独直列 1 RTT（React.cache が配列引数の参照 identity でキー衝突しないため） | 引数なし `fetchPortalSettings()`（TOP 関連 6 キー固定・1 SELECT）に統合。キー定数は `settings-keys.ts` へ集約 |
| A-3 | native モードで GET 描画毎に service-role 書き込み（placeholder 敷設） | 敷設を snapshot-schedule cron の日次実行へ移設。描画パスは「今日以降の行 0 件時のみ ensure→再読」の自己修復フォールバックに縮退（INSERT→read 順序ガード / member 検証後 write の保証は維持） |
| A-4 | `schedule_past_sessions`（追記のみ・無制限成長）を毎描画 LIMIT なし全件取得・全件 RSC 送信 → 年 +130 行 / +40〜60KB の線形劣化。全履歴 merge が videoLinkMap の ±7d 窓も無効化 | **直近 12 ヶ月に窓化（ユーザー決定）**。`parsed_date >= now-12mo`（既存 DESC index が効く）。データは削除しない。副次で video クエリ窓も有界化 |

## DB 最適化（バッチ B、schema.sql は冪等・ローカル PG16 で 2 回連続適用 + 状態実査済み）

- **B-1** `category_links(kind, posted_at)` 複合 index 追加 — TOP 毎描画の `buildSessionVideoLinkMap` と日次 fflogs-sync が最大成長テーブルを seq scan していた（既存複合は category_id 先頭で不適合）
- **B-2** Realtime publication を実購読 6 テーブル（categories / category_links / category_gphoto_albums / category_macros / recruitment_templates / schedule_session_memos）へ縮小、非購読 13 テーブルは publication から DROP + `REPLICA IDENTITY DEFAULT` へ（従来は全 19 テーブル FULL — 最多 write の出欠テーブル等が無駄な WAL/変換負荷）。購読追加時の手順コメントを 7b/8 章に明記
- **B-3** RLS の `auth.jwt()` を全 write ポリシー + self-row + blocklist + storage で `(SELECT auth.jwt() …)` に統一（initPlan、per-row → per-statement。バルク upsert で行数分評価されていた）。適用後 `pg_policies` 実査で bare 残 0
- **B-4** UNIQUE/PK が包含する冗長 index 4 本を削除
- **B-5** 非 admin 書込可カラムの長さ CHECK（NOT VALID）: `schedule_session_memos.body ≤4000 / author_name ≤100(+cntrl 禁止)`、`native_schedule_members.comment ≤500`、`native_schedule_sessions.note ≤200`（app 層の既存上限と一致）。memos はクライアント入口検証 + textarea maxLength も追加
- **B-6** `category-backgrounds` に is_admin DELETE ポリシー追加 + `deleteCategoryAction` がカテゴリ削除成功後に背景/攻略画像の**自プロジェクト** Storage オブジェクトを best-effort 掃除（prefix 厳密一致 + bucket 固定で外部 URL は対象外）
- **B-7** `/category` の累計練習時間を `practice_seconds_by_category()` RPC（STABLE / SECURITY DEFINER / search_path 固定 / REVOKE+GRANT）に置換 — 全 video 行転送 → カテゴリ数行。time-to-clear は `posted_at ≤ max(first_clear_at)+30d OR NULL` の転送上限
- **fix(seed)** `seed-demo.sql` が schema §5d で DROP 済みの legacy 列（`schedule_past_sessions.logs_url/logs_url_source`）へ INSERT しており**再適用が必ず失敗する潜在バグ**を検出・修正（子テーブル方式へ移行。ローカル実適用で seed 成功 + 再適用冪等を確認）

## バンドル/ハイドレーション（バッチ C）

- **C-1** @dnd-kit（TOP 経路唯一の静的 import 元 = 募集テンプレ popover）を popover 中身ごと `dynamic(ssr:false)` 分離。トリガーは静的維持 + hover/focus preload
- **C-2** sync モードでも常時バンドルされていた native 系 8 コンポーネント（~1,700 行）を `native-schedule/lazy.tsx`（**ssr:true** dynamic）経由に — SSR HTML 完全同一・sync では chunk ごと非ロード。`session-memo-popover`（828 行）も同方式
- **C-3** `recruitment_templates` の realtime 重複購読（2ch・変更毎フル再取得 ×2）を schedule-page-body の 1 本に集約。副次修正: TopCopy ボタンの表示ゲートが live 追従に
- **C-4** 未使用依存 `nuqs` 削除
- **計測**: 分離対象 4 モジュール + @dnd-kit が TOP 初期チャンク集合から消え async chunk へ（chunk 内容で initial=0 を確認）。移動実測 **raw 247.6KB / gzip 78.6KB**

## 安定性・堅牢性（バッチ D）

- **D-1** ログイン callback の外部 fetch 2 本（Discord guild 検証 / Supabase Admin 書込）に timeout(10s) — 外部遅延でログインが吊るのを防止
- **D-2** `addSessionLogsUrl` の孤児 placeholder 親を子 insert 失敗時に best-effort rollback（23505 = 並行挿入時は CASCADE 巻き添え回避のため rollback しない）
- **D-3** fflogs 同期に 240s 時間予算（理論最悪 ~1000s > maxDuration 300s だった）。超過時は**部分結果 + truncated** で打ち切り、auto wipe をスキップ（追加リンクのみ）・cookie 温存 → 次回全量 sync で整合。`truncated` を cron 応答 / 結果型に露出。副次修正: scrape 診断 htmlSample の return 取りこぼし解消
- **D-4** `requireSupabaseEnv()` 新設 — client/server/middleware の env `!` アサーションを欠落キー名列挙の fail-fast に置換

## 良好と確認済み（対応不要）

認可 4 層 fail-closed / 全 `.upsert()` の onConflict と UNIQUE 整合 / SECURITY DEFINER の search_path 固定 / `.single()` 誤用なし / JST 時刻処理の一貫性 / Promise.all 徹底（真の N+1 なし）/ SSRF ガード / cron 認証。`tags` 孤児は非問題（書き込みコード不存在）。

## 見送り（理由付き）

- RSC 認証の getClaims 化 — ユーザー決定で見送り（asymmetric JWT 移行が前提のため）
- クロスリクエストキャッシュ（unstable_cache）— A-2 後は利得数 ms〜十数 ms < 全書き込み経路への tag 配線漏れ＝ステール事故リスク。Speed Insights の TTFB p75 で再訪判断
- createGphotoEntryAction の RPC 化 — 二重障害時のみの孤児・手動削除可で、DEFINER 書き込み関数化のリスクに見合わず
