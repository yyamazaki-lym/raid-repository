## 🎨 TODO #60 クローズ — schedule 出欠記号にカスタムラベル (昼/夜/全 等) を許容

**狙い**: TODO #59 修正後のデモサイト動作確認で、character-sheets 側のカスタム出欠ラベル「昼 / 夜 / 全」が portal 上で全く描画されないことを確認 (rawHTML には `<span class="tag statustag is-warning is-small">夜</span>` 等が存在するのに `―` フォールバックに上書きされる)。`parse.ts` の `Attendance` 型 union が `◯ / ⏰ / △ / × / －` の 5 種固定で、`isAttendance()` がそれ以外を全 reject していたのが原因。

**実装**:
- [parse.ts](src/lib/schedule/parse.ts) `Attendance` 型を string union から `string` に拡張、`isAttendance()` を「空文字以外なら通す」に縮小。これで character-sheets が返す任意の attendance ラベル (現行確認済の昼/夜/全 + 将来増えるかもしれないユーザー定義値) を symbols 配列に保持できる
- [schedule-list.tsx](src/components/portal/schedule-list.tsx) `ATT_TONE` を `Record<string, string>` に変更、未知ラベル用の `ATT_TONE_FALLBACK` (amber 系) を新設、表示時は `ATT_TONE[att] ?? ATT_TONE_FALLBACK` で安全に lookup。`ATT_LEGEND` は引き続き標準 5 種のみを掲載 (凡例には昼/夜/全 を含めない、運用カスタム値の説明はサイト管理者が portal 内で行う想定)
- 副次修正: [parse.ts](src/lib/schedule/parse.ts) `parseSessions()` の push に `status: statusMatch[1] as SessionStatus` で raw match 値を直接使っていたのを bucket 済の `status` 変数 ("DECISION" or "CANDIDATE") に統一。空 value="" 行が status="" になって `pickNextDecision` 等で予想外の挙動を起こす可能性を排除 (defensive)

**動作影響**: 標準 5 種は従来通り (lookup hit で既存色)、昼/夜/全 等のカスタム値は amber トーンの border + 文字色で表示 + tooltip (aria-label) に表示。並び (positional alignment) も維持されるので、ユーザー欄ごとに正しいラベルが対応する。

**検証**: `tsc --noEmit` PASS。実 demo HTML (4 ユーザー × 31 行、夜/全/昼 含む) のローカル parse シミュレーションで symbols=[ヴェー★ネス: '－', 卍アゼム卍: '－', エメトセルク: '夜', ヒュトロダエウス: '夜'] のように 4 ユーザー全員にラベルが割り当てられる動作を確認。本番動作確認は次回会話で実施予定。

## 🐛 TODO #59 クローズ — schedule 時間レンジ未入力時のメンバー欄が空になる不具合を修正

**狙い**: デモサイト (`https://demo-raid-repository.vercel.app/`) で `app_settings.schedule_url` を実 URL に UPSERT 済だがメンバー欄が空のままだった件の根本対策。本番環境でも時間未入力で運用するユーザーが想定されるため、character-sheets の任意の datetitle 形式を許容する。

**真因**: [parse.ts](src/lib/schedule/parse.ts) の `RAW_DATE_RE` が `HH:MM~HH:MM` の時間レンジを必須にしていたが、character-sheets では時間未入力のまま運用するスケジュールが存在し、その場合 datetitle は `2026/05/01(金)` のように日付+曜日のみで返される。`parseRawDate()` が全行で null を返し、`parseSessions()` 全 31 行が `if (!parsed) continue;` で skip → sessions=0 → メンバー描画不能、という silent skip パスに落ちていた。throw されないため Vercel Runtime Logs にも痕跡なし。

**切り分け方法**: 当該 character-sheets URL を curl で取得 (HTTP 200, 66KB, 31 行 + 4 ユーザー、構造正常) → parse.ts 同等ロジックを node mjs スクリプトで再現 → `rawDateOk: 0` で `RAW_DATE_RE` 不一致を特定。datetitle 31 件すべて時間部分なし (`2026/05/01(金)` 形式) と確認。

**修正**:
- [parse.ts:86](src/lib/schedule/parse.ts) `RAW_DATE_RE` の時間レンジ部分を `(?:\s*(\d{1,2}):(\d{2})\s*[~〜]\s*(\d{1,2}):(\d{2}))?` で optional 化
- [parse.ts:308](src/lib/schedule/parse.ts) `parseRawDate()` で `hasTime` 判定を追加、時間未入力時は `startTime`/`endTime` に空文字、Date 構築時は JST 当日 00:00 を使うフォールバック
- [schedule-list.tsx:726](src/components/portal/schedule-list.tsx) / [next-session-card.tsx:106](src/components/portal/next-session-card.tsx): `(startTime || endTime) &&` ガードで両方空のとき時間レンジ span 自体を render skip (「 ~ 」だけが残る不格好な表示を回避)

**DB 影響**: `schedule_past_sessions.start_time/end_time` は `text NOT NULL` なので空文字 (NOT NULL を満たす) で互換、schema 変更不要。

**検証**: `tsc --noEmit` PASS。修正前後で同 curl HTML を再現スクリプトに通し、修正前 sessions=0 → 修正後 31 件正常抽出を確認。本番動作確認は次回会話で実施予定。

**動作影響**: 時間レンジ入りの既存スケジュールは従来通り (regex の non-capturing group で前方互換)、時間未入力スケジュールでは date のみで session を構築 + メンバー出席表示が機能する方向のみ。

## 🗑️ warmup-vercel GitHub Action と `/api/health` を撤廃 (TODO #11 遺物整理)

**背景**: 1.9 (2026-04-28) で導入した GitHub Actions cron `warmup-vercel` (`.github/workflows/warmup.yml`) は 5 分毎に `/api/health` を叩いて Vercel Function を warm 状態に保つ目的だったが、現状の構成では効果がほぼ無い。

**理由**:
1. portal の全ページと `/api/health` は Edge Runtime ([src/app/(portal)/layout.tsx](src/app/(portal)/layout.tsx))。Vercel Edge Function のコールドは ~50ms で、Node Lambda の数秒コールドとは桁違いに小さく warm に保つ意義が薄い。
2. Edge Function は Cloudflare Workers ベースで isolate 単位に動作するため、`/api/health` を叩いて warm になるのは「そのリクエストを処理した isolate 1 個だけ」。ユーザーが別 PoP / 別並列 instance に当たれば cold は普通に発生し、Lambda の「コンテナ再利用」モデルは存在しない。
3. GitHub Actions の cron は精度が低く `*/5 * * * *` 指定でも実際には 5〜15 分の遅延が常態 (warmup.yml のコメントにも明記)。「5 分以内に必ず叩かれる」前提は崩れている。
4. TODO #54 part2 でユーザーが体感していた「デプロイ後の重さ」の主因は Edge Function コールドではなく、新デプロイ時の RSC payload / JS chunk 初回 fetch + prefetch 暴発 + proxy.ts auth 取得遅延だった。これらは part2-c (`getClaims()` 化) と part2-d (`prefetch={false}` 化) で対処済。

**変更**: `.github/workflows/warmup.yml` 削除、[src/app/api/health/route.ts](src/app/api/health/route.ts) 削除、[src/proxy.ts](src/proxy.ts) `PUBLIC_PREFIXES` から `/api/health` 削除。今後 Node runtime の重い Server Action route を入れる場合のみ、その特定 path 単位で warmup を再検討する形に戻せばよい。
