## 📐 スケジュール: 祝日の行だけ時刻と出欠の人数 (8/8 など) が右へずれていたのをそろえた

### 狙い

実機報告「祝日だと 8/8 などの参加者人数がずれるのが気になる」。祝日の行は日付の後ろに「祝」の印 (2026-10-01 監査 U-17) が付き、そのぶん日付の幅が広がって、時刻・出欠のチップ (8/8)・アイコンが他の行より右へ押し出されていた。本番の 10/12 (スポーツの日) の行で見えていた。

### 実装

- 日程セルのアイコン枠と同じく「表単位で確保する」扱いにした。`reserveSlotsFor` が表の中に祝日が 1 日でもあるかを数え (`slots.holiday`)、祝日でない行にも印と同じ幅の見えない枠を置く
- 枠は `HolidayMark` の `placeholder` 表示。同じ文字・余白・枠線で幅をそろえ、`invisible` + `aria-hidden` で見えず読み上げもされない
- 祝日の無い表では枠を置かない (日付〜確定列の余白は従来どおり)

### 検証

- dev (demo データ) で 2026-10-08 と 2026-09-03 を一時的に祝日扱いにして、直近と過去の詳細表で時刻の左端を測った。修正前は祝日の行だけ 21px 右 (139.4 / 160.4 の 2 通り)、修正後は全行 160.4 の 1 通り。一時パッチは戻して差分が無いことを確認

## 🗄 練習ログ: FFLogs が保管扱いにした古いレポート (詳細を返さない) を、同期のたびに取り直していたのを止めた。件数は同期の結果に「取り直さない」として出る

### 狙い

本番の手動同期 (2026-10-06 10:02 JST) の runtime log に、Summary table を `This report has been archived. Subscribing users can access the report content via the /user API endpoint.` で断られたレポートが 12 件出ていた。1 件を開くと 2022 年 4 月のレポートで、FFLogs は古いログを有料会員にだけ見せる扱いにしている。取り直しても結果は変わらないのに、2026-10-05 の「詳細を取れなかったレポートは最大 3 回取り直す」(details-missing の印) に乗り、同期の枠を使っていた。出席サマリーの窓 (直近 90 日) の外なので、出席の突合とは関係ない。

### 実装

- `fflogs-detail-retry.ts` に保管扱いの判定 (`isArchivedReportError`) と、台帳に書く印を決める入口 (`detailsLedgerReason`) を追加。保管扱いなら `details-archived:<取れなかった pull 数>` を書き、`shouldRetryMissingDetails` はこの印を読まない (= 取り直さない)
- `fetchFightDetails` は保管扱いのエラーで `archived: true` を返して打ち切る。ログは警告ではなく info
- 同期結果に `detailsArchived` を足し、トーストでは「FFLogs の保管扱いで詳細が無い pull N (古いレポートのため取り直しません)」として、取り直す方の件数とは別に出す

### 検証

## 🧾 出席サマリー: 設定のメンバー一覧の下に「ログに出たが対応表に無い名前」を出し、選ぶだけでメンバーの「ログ名」に入るように。同期で参加者名を 1 人も読めなかったときも知らせるようにした

### 狙い

本番の出席サマリーが「突合できた活動日 0 日 (pull はあるのに参加者を 1 人も紐づけられなかった日が 16 日)」のままだった (2026-10-06)。原因はメンバー 7 人とも「ログ名」が空で、表示名 (Discord の名前) が FFLogs のキャラ名 (「名 姓」) と一致しないこと。ただ、何を入れればよいかは同期のトースト (最大 12 件) にしか出ず、見逃すと分からなかった。また、名前を 1 人も読めなかった場合は何も出ないため、「名前を読めていない」のか「対応表に無い」のかを画面で分けられなかった (同期結果の型のコメントには「0 / 0 でも出す」とあったが実装が無かった)。

### 実装

- 設定の Members 節の下に「ログに出たが対応表に無い名前 (N)」を出す (admin のみ、名前が無ければ出さない)。同期が書き溜めている `fflogs_attendance_unresolved` を service role で読み、名前・映っていた pull 数・最後に見た日を並べる
- 名前ごとの選択欄でメンバーを選ぶと、その人の「ログ名」の下書きに入る。保存は他の欄と同じく行の「保存」
- 今の対応表で一致する名前は外す (`stillUnresolvedNames`、突合と同じ規則)。ログ名を保存するとメンバー一覧の読み直しで一覧も取り直され、次の同期を待たずに消える。同じ名前に 2 人が当たる場合は解決しないので残る
- 同期で、詳細は取れたのに参加者名を 1 人も読めなかったレポートを数え (`attendanceNoNameReports`)、トーストで「ログ名の設定では直りません」と警告する

### 検証

- `check-attendance-unresolved.mjs` を追加 (一致した名前を外す・大文字小文字 / 全角 / 空白の違い・曖昧な名前は残す・空の名前を落とす、と配線)。8 通りの壊し方 (絞り込みなし / trim なし / admin 確認なし / 0 件を数えない / トーストなし / 割り当てない / 取り直さない / admin 以外にも出す) がすべて検査で落ちることを確認
- dev (demo データ) でサーバーが見本の名前 2 件を返す一時パッチを当て、設定の Members の下に一覧が出ること・名前をメンバーに割り当てるとその行の「ログ名」に入り「保存」ボタンが出ることを確認 (保存は押さずに破棄)。一時パッチは戻した
- 本番での確認: メンバーの「ログ名」が入った後の同期で、出席サマリーの突合できた日が 1 日以上になること

## 🔁 出席サマリー: 「ログ名」を後から入れた日を数え直せるように、突合できなかった日のレポートを取り直すボタンを追加 (幹部のみ・直近 90 日・1 回最大 25 件)。あわせて、取り直しただけのレポートを「新しいレポート」の通知に数えないようにした

### 狙い

参加者名は保存しない (W-6、名前を pull 行の隣に置くと死亡イベントと結合できるため) ので、メンバーの「ログ名」を後から入れても、突合はレポートを取り直さないとやり直せない。通常の同期 (毎朝 / 「ログを同期」) が取り直すのは直近 14 日だけなので、出席サマリーの窓 (90 日) のそれより前の日は「紐づけられなかった日」のまま残っていた (本番 2026-10-06: ログ名が空だった間の 16 日)。

調べる中で、同期が「新しいレポート」の通知の件数に**取り直したレポートも数えていた**ことが分かった (通知の説明は「新しいレポートが入ったとき」)。毎朝の同期は直近 14 日のレポートを取り直すので、新しいものが無くても「新しいレポート N 件」を投稿し得た。今回の取り直しでまとめて取り直すと大量に出るため、一緒に直した。

### 実装

- 出席サマリーに「突合できなかった日のログを取り直す」ボタン (幹部のみ・突合できなかった日があるときだけ)。押すと Server Action (`refetchUnmatchedAttendanceAction`、admin 確認が先) が対象を選び、URL を貼る取り込みと同じ経路 (`onlyCodes`) で取り直す。終わったら件数・対応表に無い名前・名前 0 件を知らせ、集計を読み直す
- 対象の選び方 (`selectRefetchTargets`、純関数): 窓の中で突合の行が 1 つも無いレポート。恒久的な取得失敗 (private など)・FFLogs の保管扱い・30 分以内に取り直したレポートは選ばない (固定外の人しか映っていないレポートなど、取り直しても紐づかないものが新しい順の先頭に居座ると、何度押しても古い日に届かないため)。一時的な失敗 (5xx・タイムアウト) は選ぶ — 動画や日程に紐づかないレポートは通常の同期が再試行しないので、外すと二度と取り直されない。新しい順に最大 25 件、残りは件数を出して「もう一度押すと続き」
- **取り直しは分類と日付を変えない** (`preserveExisting`)。保存済みの pull のカテゴリはそのまま (未分類もそのまま。新しく出た pull だけ分類)、日付と台帳のカテゴリは台帳の値を優先し、一時的な失敗でも ok だった台帳を失敗に書き換えない (後から private にされた等の恒久的な失敗は書く — 書かないと押すたびに選ばれ続ける)。通常の取り直しはカテゴリを作り直すため、URL 取り込みで選んだコンテンツや手動の割り当て (分類器で決まらないレポートの最終手段) で入っていた古い pull が未分類に落ち、練習ログから消え得た
- 取得失敗で台帳に書くとき、分かっているカテゴリと日付を null で潰さない (全経路)。台帳のカテゴリ (多数決) を取り込みの既定にはしない — 分類できない pull が多数派のコンテンツへ流れ込むため
- 読み取りに失敗したら「突合の行が無い」と扱わずにエラーで返す (全部を取り直さない)
- 件数は実際に取りに行った数で出す。対象はあるのに FFLogs の取得枠・時間切れで 1 件も取れなかったときは「取り直すレポートはありません」ではなく「今回は取り直せませんでした (残り N 件)」と出す
- 通知: 「新しいレポート」に数えるのは、台帳の fight 数が 0 (まだ pull を取り込めていない) レポートだけ。ok / 失敗では判定しないので、取り込み済みのレポートが一時的な失敗を挟んでも数え直さない。カテゴリは 0 件でも渡すので、ベスト更新・初討伐の判定は取り直しで増えた pull についても従来どおり行う
- 設定の「対応表に無い名前」の説明と、出席サマリーの「突合できなかった」の案内を、このボタンを指すように直した。ログ名を入れた人の出席が数え直されるのは、次の同期で直近 14 日と、取り直しで「1 人も紐づいていなかった日」— 他の人が紐づいている日は取り直しの対象にならないことを説明文に書いた

### 検証

- `check-attendance-refetch.mjs` を追加 (選び方 7 件・配線・通知の数え方)。12 通りの壊し方 (突合済みも選ぶ / 失敗も / 保管扱いも / 直前も / 古い順 / 重複 / 残りを数えない / admin 確認なし / 時間切れの残りを足さない / 取り直しも新しいレポートに数える / 非幹部にもボタン / 読み直さない) がすべて検査で落ちることを確認

- dev (demo データ) で「突合できなかった日 3 日」と見本の取り直し結果を返す一時パッチを当て、ボタンが出ること・押すと「4 件のレポートを取り直し、出席を 9 件紐づけました (残り 2 件 …)」と対応表に無い名前の知らせが出ることを確認 (DB には触れていない)。一時パッチは戻した
