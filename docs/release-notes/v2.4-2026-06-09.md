## 🩹 PR — TODO #82 follow-up: Vercel Marketplace「Upstash for Redis」が注入する KV_* env prefix に対応

**経緯**: TODO #82 (PR #138) で `@upstash/ratelimit` 採用後、ユーザーが Vercel Dashboard → Storage で「Upstash for Redis」(旧 Vercel KV 後継) を Connect したところ、注入された env が `UPSTASH_REDIS_REST_URL` / `UPSTASH_REDIS_REST_TOKEN` ではなく `KV_REST_API_URL` / `KV_REST_API_TOKEN` だったため、`rate-limit.ts` の `getRedis()` が env を見つけられず in-memory fallback に倒れ続ける状態だった (= 統合追加効果ゼロ)。私の知識ベースで Upstash 直接アカウント連携の prefix を前提にしてしまったミス。

**変更内容**:
- **編集** [src/lib/rate-limit.ts](src/lib/rate-limit.ts): `getRedis()` の env 読み取りを `process.env.KV_REST_API_URL ?? process.env.UPSTASH_REDIS_REST_URL` の二段 fallback に変更 (token 側も同様)。これで Vercel Marketplace 経由 (KV_* prefix) と Upstash アカウント直接連携 (UPSTASH_REDIS_REST_* prefix) の両方が動く。docstring も両 prefix の説明に更新

**触らない範囲**: ratelimiters cache / fixedWindow algorithm / fail-open フォールバックロジックは無改修。`@upstash/redis` / `@upstash/ratelimit` パッケージ side は API 完全互換 (URL/TOKEN を渡せば動く)。

**検証**: `npx tsc --noEmit` PASS / `npm run build` ✓ Compiled。本 PR merge + Vercel 再 deploy 後、ユーザー実機で `/api/page-title` を 30 回連打 → 429 + Upstash Console の Metrics で counter が増えていることを確認予定。

## 🛡️ PR — TODO #84: CSP `script-src 'unsafe-inline'` を nonce 化 (proxy.ts でリクエスト毎に注入)

**経緯**: PR #135 セキュリティ監査の Low #16 として punch list 化されていた TODO #84。XSS 経路の最後の砦である CSP `script-src` から `'unsafe-inline'` を撤去し、Next.js 公式パターンに沿って proxy.ts でリクエストごとに nonce を生成 → `<script>` タグへ自動注入する形に移行する。

**変更内容**:
- **新規** [src/lib/csp.ts](src/lib/csp.ts): `generateCspNonce()` (32 byte UUID base64) と `buildCspHeader(nonce)` を切り出し。CSP directive を一箇所に集約
- **編集** [src/proxy.ts](src/proxy.ts): リクエストごとに nonce 生成 → request header (`x-nonce` + `Content-Security-Policy`) と response header (`Content-Security-Policy`) の両方に書き込む。Next.js は request 側 CSP から `'nonce-...'` パターンを拾って framework scripts (React runtime / page bundles / 自前 inline) に自動付与する仕組み。rate-limit / redirect / public path 全 return path に `withCsp()` ヘルパで CSP を載せる
- **編集** [src/lib/supabase/middleware.ts](src/lib/supabase/middleware.ts): `updateSession` に optional 引数 `initialRequestHeaders` を追加し、proxy.ts が組み立てた x-nonce 入り Headers を `NextResponse.next({ request: { headers } })` へ橋渡し
- **編集** [src/app/layout.tsx](src/app/layout.tsx): `RootLayout` を async 化し `await headers()` で `x-nonce` を取得 → pre-hydration theme script の `nonce={...}` 属性へ焼き込む。ブラウザは security 上 nonce HTML 属性をパース後に DOM から削除するため React 19 が hydration mismatch を出す既知挙動 → `<script suppressHydrationWarning>` で抑止
- **編集** [next.config.ts](next.config.ts): 静的ヘッダの `Content-Security-Policy` を削除 (proxy.ts に統合)。他のセキュリティヘッダ (HSTS / X-Frame-Options / Referrer-Policy / X-Content-Type-Options / Permissions-Policy) は無改修で残置

**新 CSP**:
- `script-src 'self' 'nonce-{XXX}'` (production)、dev は `'unsafe-eval'` 追加 (React Refresh 用)
- `'strict-dynamic'` は採用せず、`'self'` を残して `@vercel/analytics` / `@vercel/speed-insights` の同一オリジン script (`/_vercel/insights/script.js`) を維持
- `style-src` は本 TODO スコープ外として `'self' 'unsafe-inline' https://fonts.googleapis.com` で維持。理由: React の `style={{...}}` props (inline style 属性)、Base UI / sonner / Tailwind v4 が広く inline style に依存、撤去は大規模改修

**触らない範囲**: style-src `'unsafe-inline'` (上記)、`@vercel/analytics` dev script (`va.vercel-scripts.com`) — 旧 CSP でも block されていた挙動で本 PR の regression ではない (production は同一オリジン経由なので問題なし)。`RATE_LIMIT_RULES` / 認証経路 / その他 securityHeaders は無改修。

**性能影響**: nonce ベース CSP は dynamic rendering を強制する (`headers()` 呼び出しが入るため)。元々 portal は全 route が ƒ (Dynamic) だったため、本変更による static → dynamic 退化は無し。

**検証**: `npx tsc --noEmit` PASS / `npm run build` ✓ Compiled (17 routes + middleware すべて Dynamic) / dev preview で (a) `GET /` のレスポンスヘッダに `Content-Security-Policy: ... 'nonce-{XXX}'` が含まれること、(b) `<script nonce="...">` HTML レンダリングがリロード毎に異なる nonce 値を得ること、(c) theme class (`dark theme-evercold ...`) が pre-hydration script で正しく適用されること、(d) `suppressHydrationWarning` 追加後の新規 hydration エラーが出ないこと、を確認。Vercel Analytics dev script の Failed to load は旧 CSP でも同様の挙動で regression ではない。

## 🛡️ PR — TODO #82: rate-limit を Upstash Redis 分散実装に置換 (Vercel Marketplace 連携が前提)

**経緯**: PR #135 セキュリティ監査の Medium #6 として punch list 化されていた TODO #82。`src/lib/rate-limit.ts` の in-memory fixed-window は Vercel Fluid Compute の instance 跨ぎで状態を共有しないため、実効的に `instance 数 × limit` まで緩んでおり「真の分散 rate limit」では無かった。Vercel KV は 2026 年に提供終了したため、置き換え先は Vercel Marketplace 経由の Upstash Redis 一択。

**変更内容**:
- **編集** [src/lib/rate-limit.ts](src/lib/rate-limit.ts): 全面書き換え。`@upstash/ratelimit` の `fixedWindow` algorithm を採用 (`Ratelimit.fixedWindow(limit, '${windowMs} ms')`)。Redis client は env (`UPSTASH_REDIS_REST_URL` + `UPSTASH_REDIS_REST_TOKEN`) から自動取得。Ratelimit instance は `(scope, limit, windowMs)` ごとに module-level Map にキャッシュして毎リクエスト再生成しない
- **新規挙動**: env が両方セット済 → 分散 fixed-window (Upstash Redis 経由)、いずれか欠落 → 従来通り in-memory fallback (per-instance per-IP)。fork ユーザーが Upstash 統合を入れる前でも portal が壊れない graceful degrade。Redis 呼び出しが network エラー等で失敗した場合も in-memory fallback に倒す (fail-open、`console.warn` でログ)
- **編集** [src/proxy.ts](src/proxy.ts): `applyRateLimit` を async 化 (`checkRateLimit` が async に変わったため)、`proxy()` 内 `await applyRateLimit(request)` に更新
- **追加** `package.json`: `@upstash/redis` + `@upstash/ratelimit` を dependencies に追加 (4 packages 合計)

**ユーザー側 1 回作業 (Vercel Marketplace 統合)**:
1. Vercel Dashboard → 該当プロジェクト → Storage → Browse Marketplace
2. 「Upstash Redis」を Connect
3. 環境 (Production / Preview / Development) を選んで Add
4. `UPSTASH_REDIS_REST_URL` / `UPSTASH_REDIS_REST_TOKEN` が自動で env に注入される (`vercel env pull .env.local` で local にも同期)

**触らない範囲**: RATE_LIMIT_RULES 自体 (limit / windowMs / 対象 path) は無改修。fail-open 方針 (Redis 障害時に in-memory fallback) は意図的選択 — rate-limit 自体が落ちて全リクエスト 429 になるより、瞬間的に limit が緩む方が運用上マシ。完全な fail-closed (Redis 死亡 → 全遮断) が必要なら別 TODO 化。

**検証**: `npx tsc --noEmit` PASS / `npm run build` ✓ Compiled (17 routes + middleware)。本番デプロイ前にユーザー側で Upstash Redis integration を追加 → env 確認 → `vercel env pull` で local 同期 → `npm run dev` で `/api/page-title` を 30 回超連打して 429 + Upstash dashboard で counter が増えていることを実機確認予定。

## 🧹 PR — TODO #83: sort_order 計算 RPC 化を recruitment_templates / category_macros に横展開

**経緯**: PR #135 (TODO #10) で categories / category_links の sort_order を Postgres SECURITY DEFINER RPC 化したが、`recruitment_templates` (`recruitment-templates-client.ts`) と `category_macros` (`category-macros-client.ts`) の INSERT パスには `SELECT sort_order ORDER BY ... **変更内容**:
- **編集** [supabase/schema.sql](supabase/schema.sql): Section 13c を新設し、`next_recruitment_template_sort_order()` と `next_category_macro_sort_order(p_category_id uuid)` を SECURITY DEFINER で追加 (anon, authenticated に EXECUTE GRANT)
- **編集** [src/lib/recruitment-templates-client.ts](src/lib/recruitment-templates-client.ts): `createRecruitmentTemplate` の SELECT max を `supabase.rpc('next_recruitment_template_sort_order')` 呼び出しに置換
- **編集** [src/lib/category-macros-client.ts](src/lib/category-macros-client.ts): `createCategoryMacro` の SELECT max を `supabase.rpc('next_category_macro_sort_order', { p_category_id })` 呼び出しに置換

**触らない範囲**: TODO #83 文言が併記していた `loot_items` / `mitigation_phases` / `mitigation_entries` / `strategy_docs` は schema.sql にテーブル定義だけ残る legacy で、現行 portal に対応する insert UI が存在しない (mitigation_sheet_url 等の単一文字列カラム形式に移行済) ため JS 側 sort_order race の経路自体が無い。将来 UI が復活する際に同パターンで追加する想定。categories-actions.ts の `nextImageOrder()` (category_links を `kind IN ('image','gphoto')` で絞る特殊ケース) と `category_gphoto_albums` 末尾追加も同型の TOCTOU だが、TODO #83 のスコープ外なので別 PR / 別 TODO 候補に残す。reorder 系 (`setRecruitmentTemplateOrder` / `setCategoryMacroOrder`) は index を直接 update するだけで race と無関係なので無改修。

**検証**: `npx tsc --noEmit` PASS / `npm run lint` baseline 維持。schema deploy 後 (main merge 時に GitHub Actions が本番/demo へ自動 psql) に dev preview の admin で (a) 募集テンプレ追加 → sort_order が連番、(b) カテゴリマクロ追加 → カテゴリ内 sort_order が連番で振られる、を確認予定。
