# v2.18 (2026-10-07)

## 📥 データの取り込み: Google フォトのアルバムに紐づく攻略画像が、アルバムの無い状態から取り込むと失敗していたのを直した (アルバムを先に入れる)

### 狙い

backlog の「F-3 の残り. 書き出したデータの取り込み — 未着手」に着手しようとしたところ、取り込みは #426 (2026-10-05) で実装済みで、backlog の書き換え忘れだった。既存の取り込みを調べると、コンテンツの表の並びに外部キーの順番の誤りが 1 つあった。

### 実装

- 取り込みは種類の中の表を書き出しの並び (`EXPORT_PARTS`) で入れる。content の並びが `category_links` → `category_gphoto_albums` で、`category_links.gphoto_album_id` がアルバムを参照するため、アルバムの無い DB (全データ初期化の後など) に取り込むと、アルバムに紐づく攻略画像の塊が外部キーで失敗していた。アルバムを先にした (同じファイルをもう一度取り込めば通っていた)
- `check-data-import.mjs` に、schema の `REFERENCES` と突き合わせて「種類の中では参照される表が先」「種類をまたぐ参照は、取り込み順の案内で参照される種類が先」を確かめる検査を足した
- `docs/backlog.md` の F-3 を実装済みに直した
- 既知の制約 (未対応): 日付メモの上限 (1 人 1 日付 10 件) のトリガーは、上書きになる行も数える (PostgreSQL の上書き付き INSERT でも INSERT 前のトリガーが走る)。10 件ある日付のメモを含むファイルを取り込み直すと、その塊が失敗する。直すには schema の関数の変更が要る

### 検証

- 追加した検査は、直す前の並びで `category_links → category_gphoto_albums` の 1 件だけを捕まえ、直した後は全種類で通る。種類をまたぐ参照に問題は無かった

## 🔧 攻略情報: 題名が長い (空白の無いスプレッドシートの URL など) カードで、右端の「⋮」(編集・削除) がカードの外へ押し出されて押せなかったのを直した

### 狙い

実機報告「コンテンツ名が長い場合、右端の点々が出ず、編集不可になるか」。攻略情報のリンクのカードで、題名がスプレッドシートの URL のような空白の無い長い文字列だと、右端の「⋮」(編集・削除のメニュー) が見えず、カードから編集できなかった。

### 実装

- 原因は、題名のリンク (flex の子) に `min-w-0` が無かったこと。flex の子は既定で中身の最小幅より縮まず、`break-words` (`overflow-wrap: break-word`) はその最小幅の計算に効かないので、題名の幅までリンクが広がって「⋮」をカードの外へ押し出していた
- 攻略情報のリンクのカード (`strategy-list.tsx`) と、攻略画像のカード 2 か所 (`strategy-images-list.tsx`) の題名に `min-w-0` を付けた。動画のカードは既に付いていて問題なし (同じ作りの部品を全部確認した)

### 検証

- dev (demo の零式ヘビー級の攻略情報): 実物のカードの題名を一時的に長い URL に差し替えて測った。直す前は「⋮」がカードの右端 (x=499) の外 (x=722〜750) に出て見えず、`min-w-0` を付けるとカードの中 (x=458〜486) に戻ることを確認 (測定後に元へ戻した)

## 📣 週のまとめ: 1 行目の「実戦闘 (戦闘外 N%)」を「ログ合計 (うち戦闘)」に。あわせて、1 本のログに複数日の練習が入っているときに練習ログの「ログ合計」が夜をまたいで数えていたのを直した

### 狙い

実機要望「週のまとめもログ合計にして」。前日 (v2.18 2026-10-06) に練習ログの「練習日数」の欄へログ合計を足した。週のまとめ (Discord への投稿と設定のプレビュー) の 1 行目は `練習 3 日 / 120 pull / 実戦闘 2時間30分 (戦闘外 40%)` のままで、同じ固定の練習量が画面と Discord で別の物差しになっていた。

### 実装

- 1 行目を `練習 3 日 / 120 pull / ログ合計 4時間10分 (うち戦闘 2時間30分)` にした (ユーザーの選択)。戦闘外の割合はやめた
- ログ合計は練習ログの欄と同じ `totalLogMs` (各ログの開始 (最初の pull の 30 分前まで) 〜 最後の pull の終わり、重なるログは 1 回)。週の pull をまとめて渡す
- 週のまとめの読み取りに `report_start_ms` を足した (読まないと最初の pull から数えて短くなる)
- ⚠ `totalLogMs` は、1 本のレポートの中でも **pull の間が 3 時間 (`LOG_GAP_SPLIT_MS`) 以上空いたら区間を切る**ようにした。週のまとめの検査の材料 (1 本のレポートが日をまたぐ) で、レポート単位の区間だと夜をまたぐ空き時間 (約 1 日) まで数えることに気づいた。複数日分のログを 1 本で上げた固定では、前日に入れた練習ログの「ログ合計」も同じく膨らんでいた
  - 最初は「レポート × 練習日」で切ったが、**本番の行の `session_date` はレポートにつき 1 つ** (`fflogs-fights.ts` がレポート単位で決めて全 pull に書く) なので効かないと PR のレビューで分かった。検査の材料が pull ごとに日付を変えた本番に無い形だったので通っていた。材料を本番の形 (1 本のレポートは練習日が 1 つ) にそろえた
  - 間隔で切れば、0 時をまたぐ 1 回の練習の休憩 (3 時間未満) も落とさない。2 つ目以降の区間は、その区間の最初の pull から数える (ログは夜の間も続いていたので「ログの開始」が無い)
  - 練習ログの「ログ合計」の説明 (hover、ja / en) にも「pull の間が 3 時間以上空いたら別の練習として、その間は数えない」を足した (数え方を変えて説明が古いまま残っていたのを PR のレビューで検出)。説明の 30 分・3 時間と実装の定数が一致することを `check-fflogs-progress.mjs` で突き合わせる
- 週のまとめの「うち戦闘」も pull の区間の和集合で出すようにした。同じ夜を 2 人がログに取ると pull が 2 本ずつ入り、単純に足すと「ログ合計 (和集合)」より「うち戦闘」が長くなって文面が矛盾していた (PR のレビューで検出)
- 週の区切り・送り方 (個人 ADR-005) は変えていない

### 検証

- `check-logs-weekly-summary.mjs`: 文面 (零式・絶) の期待値を新しい 1 行目に更新。日をまたぐ 1 本のレポートで 23 分 + 37 分になること、ログの開始は最初の区間にだけ入ること、本番の形 (練習日が 1 つ) でも夜を数えないこと、同じ夜のログが 2 本でも戦闘とログ合計が 1 本分になること (うち戦闘 ≤ ログ合計)、`report_start_ms` を読む配線を足した
- `check-fflogs-progress.mjs`: 本番の形の材料で、夜を数えないこと・2 つ目の区間はその最初の pull から・3 時間未満の休憩は切らない・ちょうど 3 時間で切る・並び順によらない、を足した
- 変異テスト: 14 通り (間隔で切らない・境目・しきい値・2 つ目の区間にログの開始を使う・並べ替えない・区間を伸ばさない・最後の区間を落とす・30 分の上限を外す・和集合をやめる・戦闘時間を単純な足し算に戻す・ログの開始を読まない・週より後を入れる・「うち戦闘」を落とす) がすべて検査で落ちる
- dev (demo の零式ヘビー級): 練習ログの「ログ合計 28:45:01」は変わらない (demo は 1 日 1 本のログ)。週のまとめのプレビューは demo に直近の週の練習が無いので画面では見ていない (文面は検査で固定)

## 🎞 動画: 同じ練習を別の視点で撮った動画 (題名の DAY / PART の番号と日付が同じ) を、挑戦時間・クリアまでの累計時間で二重に数えていたのを直した (長い方の 1 本だけ数える)

### 狙い

実機報告「動画を複数取り込む場合、累計挑戦時間が重複して数えられる。Day が同じ、Part が同じなどはどちらかを除外することは可能か」。本番の「絶もうひとつの未来」は、同じ練習を 2 人が別の視点で録った動画が 2 本ずつ入っていた (Discord 取り込みの「【2026 10 06】絶もうひとつの未来【DAY 7】」と、再生リスト取り込みの「FINAL FANTASY XIV 絶エデン2026 10 06 PART7」)。挑戦時間は全動画の長さの単純な合計で、14 本 22h34m とほぼ倍になっていた (練習ログのログ合計は 11:06:50)。

### 実装

- 純関数 `challengeTime` (`src/lib/video-challenge-time.ts`) で、同じ練習とみなした組は長い方の 1 本だけ数える (ユーザーの選択: 番号 + 日付)
  - 同じ YouTube の動画 (`youtu.be/ID` と `watch?v=ID` のような URL の書き方違い)。組の代表は番号と日付の読める題名を優先する (題名が URL のままの行があっても、渡す順で結果が変わらない)
  - 題名の練習の番号 (`DAY 7` / `PART7` / `7日目` / `パート7`、全角も) と、題名の日付 (全角も。無ければ投稿日時、それも無ければ行の作成日時の JST 暦日) が**両方とも同じ**動画のうち:
    - **系列が違う** (題名の数字を伏せた形が違う = 別の人・別の付け方) なら、分割の印 (前半 / 後半 / 続き など) が無く、日付と番号のほかの数字 (`7-1` と `7-2`、`M3S` と `M4S`、`①` と `②`) が食い違わないとき
    - **系列が同じ**、または**番号の語までの書き方が同じ** (同じ投稿者の付け方。例「【# # #】絶もうひとつの未来【day #」) なら、題名がまったく同じとき (上げ直し) だけ。同じ投稿者が 1 本目に印を付けずに分割した (「【DAY 7】」と「【DAY 7-2】」) 動画を、別の人の視点と取り違えて消さないため (PR のレビューで検出)
  - ⚠ 日付は前後 1 日を許さない。本番で DAY 1 が「2026 09 18」、PART1 が「2026 09 19」だったのは題名の付け間違いで、ユーザーが題名を直す (2026-10-07)。最初は 1 日を許して組にしたが、Part を毎日 1 から数え直す付け方で隣の日の別の練習を消すと PR のレビューで分かった
  - ⚠ 絶の題名の `P1` `P2` はフェーズの意味なので Part と読まない。`Day 3 Part 2` のように両方ある題名は、両方が一致するときだけ組にする
  - 番号・日付の分からない動画は今までどおり足す (間違えるなら数えすぎの側)。組はロケールに依存しない比較で作るので、サーバー (一覧カード) とブラウザ (動画タブ) で同じ結果になる
- 挑戦時間を出す 6 か所をすべてこの関数に通した (今までは別々に単純な足し算をしていた): 動画タブの「コンテンツ挑戦時間」/「累計練習時間」/「クリアまでの累計時間」、選択モードの「クリアまでの累計時間として保存」、コンテンツ一覧のカード (挑戦時間・クリアまでの時間)、メンテの「クリア日の一括設定」の結果。日付の渡し方 (投稿日時、無ければ行の作成日時) も 4 か所でそろえた
  - 一覧カードの挑戦時間は SQL の単純な合計 (RPC `practice_seconds_by_category`) をやめ、動画の行 (7 列) を全ページ読んで集計する (番号と日付の判定は SQL で書けない)。RPC は schema に残してある (schema は変えていない)
- 動画タブのバッジの hover に「同じ練習の別の動画 N 本は数えていません。長い方の 1 本だけ数えます」を出す (クリア済みの「クリアまでの累計時間」はその範囲での本数)。選択モードで保存するときの確認文にも同じ本数を出す (保存した値は手動入力として自動の値より優先されるので、少ない値と気づかずに保存しないように)
- 「再生時間未取得 N 件」の N は今までどおり長さの無い動画の本数 (組になっていても数える)
- 手動で入れた「クリアまでの累計時間」があるコンテンツは、今までどおりその値が優先

### 検証

- `scripts/check-video-challenge-time.mjs` (新規): 本番の 14 本の題名と長さで、題名を直す前は 6 組 + 2 本 (12h39m)、直した後は 7 組 (11h27m)、渡す順によらないこと。別の練習を消さない場合 (1 日違い・毎日数え直す Part・2 系列で本数が違う日・7-1/7-2・前半/後半・①/②・M3S/M4S・層違いの系列違い・番号違い・Day と Part の両方・番号なし・日付なし・全角の日付)、まとめる場合 (上げ直し・ほかの数字が片方にしか無い系列違い・同じ YouTube の動画・代表は番号の読める題名・投稿日時の JST 暦日・ロケールによらない)、長さの分からない動画、同じ投稿者が印を付けずに分割 (DAY 7 と DAY 7-2・②・延長・午後)、別の投稿者でも分割の印があれば組にしない、配線 (6 か所・日付の渡し方・確認文・クリアまでの本数)。18 通りの壊し方がすべて落ちることを確認
