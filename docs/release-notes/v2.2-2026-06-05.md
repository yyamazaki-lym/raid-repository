## 🔧 PR #134 — Discord URL 取り込み cron を 23:00 JST → 01:00 JST に変更

**経緯**: 運用上の都合により Discord URL 取り込み cron (`/api/cron/import-discord`) の発火時刻を 23:00 JST から日付が変わった直後の 01:00 JST に後ろ倒し。23:00 JST 帯は通常 raid 直後でチャンネルへの投稿が活発な時間帯にあたり、当日分の URL が取り込まれずに翌日 23:00 までずれ込むケースを避けるのが目的。

**変更内容**:
- **編集** [vercel.json](vercel.json): `crons[].schedule` を `0 14 * * *` (= 14:00 UTC = 23:00 JST) → `0 16 * * *` (= 16:00 UTC = 01:00 JST) に差し替え。Vercel Hobby plan の sub-daily 制約 (日 1 回以下) を満たす daily cron のまま、時刻だけ移動
- **編集** [src/app/api/cron/import-discord/route.ts](src/app/api/cron/import-discord/route.ts): JSDoc 冒頭の `Schedule defined in vercel.json: ...` を新値 (`0 16 * * *` (01:00 JST)) に同期
- **編集** [src/app/api/cron/notify-native-schedule/route.ts](src/app/api/cron/notify-native-schedule/route.ts): JSDoc を現行設計 (Supabase pg_cron hourly 発火 + route 側 HH gate で目標時のみ通知) に書き直し。旧コメントが「Vercel Cron で 12:00 JST 発火」前提のままだった棚卸し痕跡を解消

**変更しない範囲**: `runDiscordImport()` 本体ロジックは無改修 (発火時刻に依存しない設計、各 channel の最新 500 件を都度遡るだけ)。`/api/cron/snapshot-schedule` (21:50 JST) と Supabase pg_cron 経由の `notify-native-schedule` (毎時 0 分 + HH gate) の schedule 自体は無関係につき touch なし。

**検証**: vercel.json の差分が 1 行 (`14` → `16`) のみで型・実行コードに影響なし。本番 deploy 後、Vercel Dashboard → Cron で次回発火が `01:00 JST` 表示に切り替わっていることを確認 + 翌日 01:00 JST 通過後に Vercel logs で発火痕跡を目視確認。

## 🐛 PR #133 — Vercel cron が anon 権限で動いて RLS に弾かれ、Discord URL 取り込み / schedule snapshot が 4/29 以降ほぼ停止していた問題を修正

**症状**: 6/02 (火) raid 開催日が確定マーク済にもかかわらず portal の過去日程に並ばず、当日の動画 URL も Discord 23:00 JST cron で取り込まれない事象をユーザーから報告。Supabase で `schedule_past_sessions` を直接見ると 5/26 を最後に snapshot row が 1 件も追加されていなかった。

**真因**: TODO #36 phase 2 ([commit 77e4e99](https://github.com/yyamazaki-lym/raid-repository/commit/77e4e99), 2026-04-29) で `category_links` / `schedule_past_sessions` を含む 18 テーブルの RLS を `TO authenticated WITH CHECK ((auth.jwt() -> 'app_metadata' ->> 'is_admin') = 'true')` に厳格化した際、cron route が呼んでいる shared function ([runDiscordImport](src/lib/server/discord-import.ts:75) / [runScheduleSnapshot](src/lib/server/schedule-snapshot.ts:25)) は **cookie 経由の `createClient()`** を使い続けていた。Vercel cron は HTTP fetch なので cookie を持たず実質 anon role に降格、INSERT / UPDATE / DELETE が全 RLS deny。Vercel Functions logs に `new row violates row-level security policy for table 'category_links'` warning が連発していたのに 200 status で応答していたため気付けなかった。Settings dialog からの手動「Import now」「出席状況を即時保存」ボタン経路は admin cookie 経由なので RLS 通過しており、ユーザーが定期的に手動押下していた間は部分的にデータが残っていた (5/07 / 5/12 / 5/26 の snapshot row はすべて手動押下の痕跡)。先行する notify-native-schedule cron ([PR #59](https://github.com/yyamazaki-lym/raid-repository/pull/59)) は同じ問題を回避するため既に `createSupabaseServiceRoleClient()` 化済だったが、import / snapshot は service role 化漏れだった。

**変更内容**:
- **編集** [src/lib/server/discord-import.ts](src/lib/server/discord-import.ts): import line と本体 3 箇所 (`runDiscordImport` / `importChannel` / `maybeAutoLinkSheetUrls`) の `await createClient()` を `createSupabaseServiceRoleClient()` に差し替え。service role は cookie 不要なので `await` も除去
- **編集** [src/lib/server/schedule-snapshot.ts](src/lib/server/schedule-snapshot.ts): 同パターンで `runScheduleSnapshot` の 1 箇所を差し替え

**認可の二重化**: cron route 入口で `Bearer ${CRON_SECRET}` または `x-vercel-cron` header を必須にする gate、Server Action 入口 ([importDiscordLinksNow](src/lib/server/categories-actions.ts:365) / [snapshotScheduleNow](src/lib/server/categories-actions.ts:1067)) で `assertAdminResult()` admin gate が立っているので、shared function を service role に上げても service role 漏れ出しリスクは増えない。

**触らない範囲**: vercel.json の cron schedule (= 別 PR で 01:00 JST に変更予定)、route ファイルの auth 経路、Settings dialog UI、`createSupabaseServiceRoleClient()` 実装側 ([server.ts:79](src/lib/supabase/server.ts:79))、他の Server Action 系 (admin 経路の cookie auth 維持)。

**検証**: 本 PR merge & deploy 後、Vercel Dashboard → Cron Jobs から `/api/cron/import-discord` と `/api/cron/snapshot-schedule` を Run ボタンで手動 trigger、Functions logs に **`row violates row-level security` warning が一切出ないこと** を確認。続けて Supabase Studio で `SELECT count(*) FROM category_links WHERE source='discord' AND created_at > now() - interval '5 minutes'` で取り込み件数 > 0、char-sheets に DECISION 行があれば `SELECT * FROM schedule_past_sessions WHERE raw_date LIKE '2026/06/%' AND source='snapshot'` で 6 月行の出現を確認。
