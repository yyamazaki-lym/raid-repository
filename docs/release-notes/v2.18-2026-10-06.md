## 🔁 出席サマリー: 「ログ名」を後から入れた日を数え直せるように、突合できなかった日のレポートを取り直すボタンを追加 (幹部のみ・直近 90 日・1 回最大 25 件)。あわせて、取り直しただけのレポートを「新しいレポート」の通知に数えないようにした

### 狙い

参加者名は保存しない (W-6、名前を pull 行の隣に置くと死亡イベントと結合できるため) ので、メンバーの「ログ名」を後から入れても、突合はレポートを取り直さないとやり直せない。通常の同期 (毎朝 / 「ログを同期」) が取り直すのは直近 14 日だけなので、出席サマリーの窓 (90 日) のそれより前の日は「紐づけられなかった日」のまま残っていた (本番 2026-10-06: ログ名が空だった間の 16 日)。

調べる中で、同期が「新しいレポート」の通知の件数に**取り直したレポートも数えていた**ことが分かった (通知の説明は「新しいレポートが入ったとき」)。毎朝の同期は直近 14 日のレポートを取り直すので、新しいものが無くても「新しいレポート N 件」を投稿し得た。今回の取り直しでまとめて取り直すと大量に出るため、一緒に直した。

### 実装

- 出席サマリーに「突合できなかった日のログを取り直す」ボタン (幹部のみ・突合できなかった日があるときだけ)。押すと Server Action (`refetchUnmatchedAttendanceAction`、admin 確認が先) が対象を選び、URL を貼る取り込みと同じ経路 (`onlyCodes`) で取り直す。終わったら件数・対応表に無い名前・名前 0 件を知らせ、集計を読み直す
- 対象の選び方 (`selectRefetchTargets`、純関数): 窓の中で突合の行が 1 つも無いレポート。恒久的な取得失敗 (private など)・FFLogs の保管扱い・30 分以内に取り直したレポートは選ばない (固定外の人しか映っていないレポートなど、取り直しても紐づかないものが新しい順の先頭に居座ると、何度押しても古い日に届かないため)。一時的な失敗 (5xx・タイムアウト) は選ぶ — 動画や日程に紐づかないレポートは通常の同期が再試行しないので、外すと二度と取り直されない。新しい順に最大 25 件、残りは件数を出して「もう一度押すと続き」
- **取り直しは分類と日付を変えない** (`preserveExisting`)。保存済みの pull のカテゴリはそのまま (未分類もそのまま。新しく出た pull だけ分類)、日付と台帳のカテゴリは台帳の値を優先し、一時的な失敗では台帳を書き換えない (private が確定したときだけ書く — 書かないと押すたびに選ばれ続ける。v2 が権限エラーで v1 が一時的に失敗しただけの「非公開の可能性」は書かない。書くと v1 で読めていた限定公開のレポートが非公開の失敗に化ける)。台帳を読めなかったときは取り直しをやめる。通常の取り直しはカテゴリを作り直すため、URL 取り込みで選んだコンテンツや手動の割り当て (分類器で決まらないレポートの最終手段) で入っていた古い pull が未分類に落ち、練習ログから消え得た
- 取得失敗で台帳に書くとき、分かっているカテゴリと日付を null で潰さない (全経路)。台帳のカテゴリ (多数決) を取り込みの既定にはしない — 分類できない pull が多数派のコンテンツへ流れ込むため
- 読み取りに失敗したら「突合の行が無い」と扱わずにエラーで返す (全部を取り直さない)
- 取り直せなかったレポートと理由を、ボタンの下に出す (取り直しは一時的な失敗を台帳に書かないので、理由はここと runtime logs にしか残らない)。件数は実際に取りに行った数で出す。対象はあるのに FFLogs の取得枠・時間切れで 1 件も取れなかったときは「取り直すレポートはありません」ではなく「今回は取り直せませんでした (残り N 件)」と出す
- 通知: 「新しいレポート」に数えるのは、台帳の fight 数 (前回 FFLogs が返したボス戦の数) が 0 で、保存済みの pull も無いレポートだけ。ok / 失敗では判定しないので、取り込み済みのレポートが一時的な失敗を挟んでも数え直さない。取り直しでは、新しく出た pull のカテゴリだけを通知の判定に渡す — 保存済みの pull しか無いカテゴリを渡すと、通知の記録が無い古いコンテンツ (前の tier 等) について、何か月も前の討伐が「初討伐」として投稿され得た (投稿は取り消せない)。通知の判定 (`detectLogsEvents`) 自体は変えない (記録の無いカテゴリで初討伐を止めると、取り込み済みのレポートの pull が後から作ったカテゴリへ初めて入ったときの本物の初討伐まで止まる。一度入れて戻した)。カテゴリは 0 件でも渡すので、ベスト更新・初討伐の判定は取り直しで増えた pull についても従来どおり行う
- 設定の「対応表に無い名前」の説明と、出席サマリーの「突合できなかった」の案内を、このボタンを指すように直した。ログ名を入れた人の出席が数え直されるのは、次の同期で直近 14 日と、取り直しで「1 人も紐づいていなかった日」— 他の人が紐づいている日は取り直しの対象にならないことを説明文に書いた

## 🔍 練習ログ: 自動発見が、取り込み済みのレポートを同期のたびに「新しいレポート N 件を候補に追加」と数え直していたのを直した。URL 取り込み・出席の突合の取り直しでは一覧を引かないようにした

### 狙い

本番 (2026-10-06) で「ログを同期」を押すたびに「自動発見: 新しいレポート 12 件を候補に追加しました」と出ていた。自動発見 (W-5) は、一覧に出たレポートが発見済みかどうかを動画・日程の紐づき (`collectReportRefs`) だけで判定し、台帳 (`fflogs_report_syncs`、取り込み済みの一覧) を見ていなかった。そのため、取り込み済みでも動画や日程に紐づいていないレポートが毎回「新しい」と数えられ、新しいものが無いときの「新しいレポートはありませんでした」も出なかった。

あわせて、マージ前のレビューで、URL 取り込みと出席の突合の取り直し (コード指定の取り込み) でも自動発見が毎回走り、結果を使わないのに一覧 API (経路 1 本あたり最大 20 秒) が同期の時間予算と FFLogs のポイントを使っていたことが分かった。

### 実装

- 一覧に出たコードだけ台帳を引き (最大 25 件)、`sortDiscoveredReports` (純関数、`fflogs-report-source.ts`) で「今回の同期で扱うもの」と「新しく見つけたと数えるもの」に分ける

  - 台帳に無いものだけを数え、発見の枠 (25 件) もそれにだけ使う
  - 台帳を読めなければ従来どおり全部を新しいと数える (取り込みは止めない)
- コード指定の取り込み (URL 取り込み・出席の突合の取り直し) では自動発見をしない

## 🗑 スケジュール: 「過去ログから消す」で消しても、開催時刻を変える前の同じ日の行が代わりに出て、簡易ログ・詳細ログに日付が残っていたのを直した (出席サマリーでも数えない)

### 狙い

実機報告「詳細ログから過去ログから消すボタンで削除しても簡易ログの方に日付が残る」。本番の除外一覧には `2026/10/02(金) 21:30~0:00` だけが入っていた。同期式の過去の日程は rawDate (日付 + 時刻) ごとに 1 行で、10/02 には開催時刻を変える前の `22:00~0:00` の行も残っている (2026-10-05 の重複まとめ #432 で 1 つにまとめて表示していた)。除外は rawDate の 1 行にしか印を付けないので、21:30 の行を消すと 22:00 の行が代わりに表示され、簡易ログには 10/02 が、詳細ログには時刻だけ変わった 10/02 が残っていた。

### 実装

- 重複まとめの計画 (`planPastSessionMerge`) に、除外した行 (`excluded`) を渡せるようにした。除外した行と**同じ開催** (同じ JST 暦日で時間帯が重なる) の行は、保存済みの行も、それを実開催の証拠にするデイコードの行も外す。昼と夜のように時間帯が重ならない開催は残す
- 表示 (`mergeStoredPastSessions`) は除外した行も読み (`fetchExcludedPastSessions` に時刻と読み込み窓を足した)、計画に渡す。読めなければ従来どおり (除外した rawDate の行だけが消える)
- 出席サマリー (同期式) も除外した行を同じ問い合わせで読み、同じ開催を数えない
- データは書き換えない。除外の解除 (設定の「過去ログから除外中の日程」の ↺) で、まとめた日ごと元に戻る。本番の 10/02 は、このデプロイで追加の操作なしに消える

### 検証

- `check-past-session-dedup.mjs` に「除外した開催」の検査 (本番の 10/02 の再現・昼と夜・デイコードの行・除外なし・他の行から証拠を得ない) と配線を足した。6 通りの壊し方がすべて検査で落ちることを確認
- demo は自前作成式で同期式の過去ログを再現できないため、画面での確認はデプロイ後に本番で行う (10/02 が簡易ログ・詳細ログから消えること)

## 🔁 出席サマリー: 「紐づいている日も含めて取り直す」を追加 (一部の人のログ名を後から入れたとき、その人の古い日も数え直せる)。参加者名を取れないレポート (代替経路で読んだもの) は取り直さず、失敗が続くレポートは後回しにする

「突合できなかった日のログを取り直す」(同日の先の項目) を本番で押し、出席サマリーの突合できた日は 5 日から 16 日になった。そのうえで残っていた 3 点を直す。

- 取り直しの対象は「1 人も紐づいていない日」だけなので、一部のメンバーだけ「ログ名」を後から入れた場合、他の人が紐づいている日は選ばれず、その人の古い日が数え直されなかった
- 代替経路 (v1 / cookie) でしか読めない限定公開のレポートは、pull の詳細 (参加者名を含む) を取らないので何度取り直しても紐づかず、押すたびに選ばれて枠を使っていた
- 削除済みなどで取り直しに失敗し続けるレポートも、押すたびに選ばれていた (取り直しの一時的な失敗は台帳に書かない作りのため、選び方に手がかりが無かった)

### 実装

- 出席サマリーに「紐づいている日も含めて取り直す」(幹部のみ・突合できた日があるとき)。Server Action に `includeMatched` を渡し (client の値は `=== true` のときだけ採る)、突合の行があるレポートも選ぶ。30 分以内に取り直したものは飛ばすので、押すたびに次の 25 件へ進む
- 代替経路で読めたレポートは台帳の reason に `via-fallback` を書き、取り直しの対象から外す。v2 で読めた同期で印は消える
- 取り直しの一時的な失敗は、取り込み済み (ok) の行の reason に `refetch-failed:<回数>` だけを残す (ok・日付・分類は変えない。details-missing などの他の印は上書きしない)。回数の多いものは後回しにし、3 回で外す。数えるのはそのレポート固有の失敗 (存在しない・空の応答) だけで、通信・認証 (401)・5xx・429 のような全体の障害や、限定公開の代替経路の連鎖は数えない (障害中に押した回数でレポートが対象から外れたままになるため)。取り込みに成功した同期で reason は書き直されて印は消える
- reason は成功の行の画面には出ない (失敗の一覧と診断は ok = false の行だけを読む。ADR-009)
- 詳細 (参加者名を含む) を途中のバッチで打ち切ったレポート (時間切れ・429・5xx) は、出席を記録しない。出席の行は (レポート, 人) で上書きするので、途中までの pull 数で既存の正しい行を小さく書き換え、全部に出た人に「ごく一部しか映っていない」のズレが付いていた。台帳の details-missing の印で、次に全部取れたときに記録される (通常の同期にも同じ判定が効く)

### 検証

- `check-attendance-refetch.mjs` (紐づいている日も含める・代替経路の印・失敗の後回しと上限・配線) と `check-fflogs-sync-visibility.mjs` (印の読み書き) に検査を足した。10 通りの壊し方がすべて検査で落ちることを確認。マージ前のレビュー (指摘ごとの反証) で通った 2 件 (全体の障害を失敗の回数に数える・打ち切った詳細で出席を上書きする) を直し、6 通りの壊し方も検査で落ちることを確認
- 本番での確認: 「紐づいている日も含めて取り直す」で、ログ名を後から入れた人の古い日の出席が増えること

## 👤 メンバー: 「シートでの旧名」を追加。スケジュールのシートを切り替えたり名前を変えたりする前の日の回答を、過去ログと出席サマリーで今のメンバーに結びつけられるようにした

## 🏷 練習ログ: 「ミス注釈の傾向」の各行にマウスを載せると、その注釈が付いた pull の日時・ティア通算の番号・一言メモが出るように

### 狙い

実機要望「ミス注釈の傾向はマウスオーバーなりで見えるようにしてほしい」。傾向カードはタグごとの件数 (「散開 / 位置 ×7」など) しか出さず、どの pull に付いた注釈なのか、一言メモに何が書いてあるのかは、Discord 用の振り返りをコピーするか pull を 1 つずつ開かないと分からなかった。

### 実装

- 傾向の各行の `title` に、そのタグの注釈を 1 件 1 行で出す。書き方は初討伐カードの hover (`floorClearHover`) に揃えた: `2026-09-04 21:48 開始の pull (ティア通算 191 pull 目): 一言メモ`。練習ログの他の hover もブラウザの `title` なので、出し方も同じにした (会社側 playbook「同じツール内で同じ機能のUIは揃える」の手順 1・2)
- 新しい pull が先。1 行に出すのは 15 件までで、残りは「ほか N 件」
- ⚠ Windows の Chrome / Edge は `title` を 1024 文字で切る (Chromium の `kMaxTooltipLength`。他の OS は 2048)。行数だけで切ると、メモが長いときに末尾の行と「ほか N 件」が黙って消える (PR のレビューで検出)。hover ではメモを 40 字で切り、全体を 1000 字の予算に収め、出せなかった件数の行は必ず残す (`fitTooltipLines`)。メモの全文は pull の展開行で見る
- 日付はセッションの日 (`session_date`) を優先し、時刻は JST 固定 (初討伐カードと同じ)
- ティア通算の番号は初討伐カードと同じ明細 (`tierFights`) を開始時刻の順に数える。明細が打ち切られている (`truncated`) ときは番号を出さない (古い pull が落ちて番号が過小になる)。明細に無い pull の注釈は「日時の分からない pull (明細の範囲外)」とし、注釈を付けた日時で代用しない (pull の日時と取り違える)
- 個人タグ (`scope='self'`) は傾向の集計と同じく出さない
- 明細の組み立ては純関数 `pullNoteDetailsByTag` (`src/lib/logs/pull-note-tags.ts`)

### 検証

- `check-pull-note-tags.mjs` に、並び (新しい pull が先・明細に無い注釈は後ろ)、メモの空白の扱い、タグの鍵と件数が `countPullNoteTags` と一致すること、打ち切り時に番号を出さないこと、番号が渡す順によらないこと、ティア外の pull は日時だけになること、を足した。7 通りの壊し方 (並びの逆転・番号を並べ替えずに数える・打ち切りでも数える・タグの空白・メモの改行など) がすべて検査で落ちることを確認。文字数の予算 (予算を超えない・見えていない件数の行が必ず残る・予算の境目・改行の分も数える) の検査も足し、6 通りの壊し方がすべて落ちることを確認
- dev (demo の「至天の座アルカディア零式：ヘビー級」) で、「散開 / 位置 ×7」に 7 行、「AoE 被弾 ×6」に 6 行が出て、通算の番号がセッションの並び (9/04 は 185〜194 pull 目) と合うことを確認。demo の絶には注釈が無いので、絶では実物を見ていない (同じ関数を通る)
- ⚠ ブラウザの `title` なので、タッチ端末では出ない (練習ログの他の hover と同じ)

## ⏱ 練習ログ: 「練習日数」の下にログの合計時間 (各ログの開始〜最後の pull の終わり。pull の間の休憩を含む) を出すように

### 狙い

実機要望「練習日数に戦闘時間でなく Logs の総合計時間を入れたい」。練習ログで時間として出ていたのは戦闘時間 (日ごとの行の「戦闘 44:19」、フェーズ滞在時間の合計) だけで、pull の間の休憩・作戦会議を含めて「何時間練習したか」は出ていなかった。

### 実装

- 「練習日数」のタイルの下に `ログ合計 28:45:01` を出す。hover に定義 (各ログの開始から最後の pull の終わりまで、休憩を含む、重なるログは 1 回) を出す
- 長さの定義はユーザーの選択で「ログの開始 (`report_start_ms`) 〜 最後の pull の終わり」。FFLogs のレポートの長さ (endTime − startTime) とほぼ同じで、違いは最後の pull の後にログを止めるまでの数分だけ。終了時刻は保存していないので、schema を変えずに過去のログにもすぐ出せるこの形にした (終了時刻を保存する案は schema 変更 + 取り直しが要るので見送り)
- 同じ時間帯に重なるログ (2 人が上げた・分割した) は 1 回だけ数える。日ごとに出して足し合わせない (日をまたいだレポートの開始が両方の日に入って二重になる)
- 数える pull は練習日数と同じ (`tierFights`)。明細が打ち切られているときは「(表示中の分)」を添える
- 純関数 `totalLogMs` (`src/lib/fflogs-progress.ts`)
- タイルの補足行 (`StatCard` の `sub`) を、末尾で「…」に切らず折り返すようにした。375px 幅ではタイルの内側が 130px しかなく、「ログ合計 28:45:01」でちょうど一杯。100 時間を超えたり注記が付いたりすると、時間や注記が切れて読めなくなるため

### 検証

- `check-fflogs-progress.mjs` に検査を追加 (休憩を含む・別の時間帯は足す・重なり / 包含は 1 回・接するログ・渡す順によらない・ログの開始が無い / pull より後・数でない時刻・終わりが開始より前)。9 通りの壊し方のうち 8 通りが落ちることを確認。残る 1 通り (接する区間をつなげない) は合計が変わらない等価な変更
- dev (demo の「至天の座アルカディア零式：ヘビー級」): 「24 日 / ログ合計 28:45:01」と hover の説明が出ることを確認 (1 日あたり約 1 時間 12 分。demo のセッション、例えば 9/04 は 21:00 開始で 10 pull・戦闘 44:41、と見合う)。375px 幅で、長い値 (「ログ合計 128:45:01 (表示中の分)」を一時的に入れて測定) がはみ出さず 2 行に折り返すことを確認
