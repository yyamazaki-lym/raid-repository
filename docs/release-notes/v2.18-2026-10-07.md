## 📥 データの取り込み: Google フォトのアルバムに紐づく攻略画像が、アルバムの無い状態から取り込むと失敗していたのを直した (アルバムを先に入れる)

### 狙い

backlog の「F-3 の残り. 書き出したデータの取り込み — 未着手」に着手しようとしたところ、取り込みは #426 (2026-10-05) で実装済みで、backlog の書き換え忘れだった。既存の取り込みを調べると、コンテンツの表の並びに外部キーの順番の誤りが 1 つあった。

### 実装

- 取り込みは種類の中の表を書き出しの並び (`EXPORT_PARTS`) で入れる。content の並びが `category_links` → `category_gphoto_albums` で、`category_links.gphoto_album_id` がアルバムを参照するため、アルバムの無い DB (全データ初期化の後など) に取り込むと、アルバムに紐づく攻略画像の塊が外部キーで失敗していた。アルバムを先にした (同じファイルをもう一度取り込めば通っていた)
- `check-data-import.mjs` に、schema の `REFERENCES` と突き合わせて「種類の中では参照される表が先」「種類をまたぐ参照は、取り込み順の案内で参照される種類が先」を確かめる検査を足した
- `docs/backlog.md` の F-3 を実装済みに直した
- 既知の制約: 日付メモの上限 (1 人 1 日付 10 件) のトリガーは、上書きになる行も数える (PostgreSQL の上書き付き INSERT でも INSERT 前のトリガーが走る)。10 件ある日付のメモを含むファイルを取り込み直すと、その塊が失敗する。直すには schema の関数の変更が要る → 次の part で直した

### 検証

- 追加した検査は、直す前の並びで `category_links → category_gphoto_albums` の 1 件だけを捕まえ、直した後は全種類で通る。種類をまたぐ参照に問題は無かった

## 📥 データの取り込み: 日付メモが 10 件ある日付を含むファイルを取り込み直すと、上限に引っかかって失敗していたのを直した (上書きになるメモは数えない)

### 狙い

日付メモの上限 (1 人 1 日付 10 件、#423) のトリガー `schedule_session_memos_enforce_limit` は `BEFORE INSERT` で、PostgreSQL では上書き付きの INSERT (`ON CONFLICT DO UPDATE`、取り込みの upsert) でも走る。数える条件が「同じ人・同じ日付の行」だけだったので、上書きになる行自身も数えてしまい、10 件ある日付のメモを含むファイルを取り込み直すとその塊が `memo_limit_per_date` で失敗していた。

### 実装

- `supabase/schema.sql` のトリガー関数で、数える条件に `AND id <> NEW.id` を足した (上書きになる行自身は数えない)。`id` は `DEFAULT gen_random_uuid()` で、既定値は INSERT 前のトリガーより先に入るので、画面からの新規作成 (`id` を送らない) でも `NEW.id` は NULL にならない
- 移した行・新しい行は今まで通り数える: 上書き 10 件 + 新しい 1 件の塊、別の日付の行を満杯の日付へ移す上書きは弾く
- `check-memo-permissions.mjs` に「上書きになる行自身は数えない」の検査を足した

### 検証

- 実際の `schema.sql` からトリガー関数を切り出して PGlite で流した。直す前の schema では「10 件ある日付を全部上書き」が `memo_limit_per_date` で失敗し、直した後は通って 10 件のまま本文が更新される。11 件目 (`id` 省略)・上書き 10 件 + 新しい 1 件・別の日付から満杯の日付へ移す上書きは、直した後も弾く。所有者不明の行は数えない (従来通り)

## 🔧 攻略情報: 題名が長い (空白の無いスプレッドシートの URL など) カードで、右端の「⋮」(編集・削除) がカードの外へ押し出されて押せなかったのを直した

### 狙い

実機報告「コンテンツ名が長い場合、右端の点々が出ず、編集不可になるか」。攻略情報のリンクのカードで、題名がスプレッドシートの URL のような空白の無い長い文字列だと、右端の「⋮」(編集・削除のメニュー) が見えず、カードから編集できなかった。

### 実装

- 原因は、題名のリンク (flex の子) に `min-w-0` が無かったこと。flex の子は既定で中身の最小幅より縮まず、`break-words` (`overflow-wrap: break-word`) はその最小幅の計算に効かないので、題名の幅までリンクが広がって「⋮」をカードの外へ押し出していた
- 攻略情報のリンクのカード (`strategy-list.tsx`) と、攻略画像のカード 2 か所 (`strategy-images-list.tsx`) の題名に `min-w-0` を付けた。動画のカードは既に付いていて問題なし (同じ作りの部品を全部確認した)

### 検証

- dev (demo の零式ヘビー級の攻略情報): 実物のカードの題名を一時的に長い URL に差し替えて測った。直す前は「⋮」がカードの右端 (x=499) の外 (x=722〜750) に出て見えず、`min-w-0` を付けるとカードの中 (x=458〜486) に戻ることを確認 (測定後に元へ戻した)

## 🎞 動画: 同じ練習を別の視点で撮った動画 (題名の DAY / PART の番号と日付が同じ) を、挑戦時間・クリアまでの累計時間で二重に数えていたのを直した (長い方の 1 本だけ数える)

### 狙い

実機報告「動画を複数取り込む場合、累計挑戦時間が重複して数えられる。Day が同じ、Part が同じなどはどちらかを除外することは可能か」。本番の「絶もうひとつの未来」は、同じ練習を 2 人が別の視点で録った動画が 2 本ずつ入っていた (Discord 取り込みの「【2026 10 06】絶もうひとつの未来【DAY 7】」と、再生リスト取り込みの「FINAL FANTASY XIV 絶エデン2026 10 06 PART7」)。挑戦時間は全動画の長さの単純な合計で、14 本 22h34m とほぼ倍になっていた (練習ログのログ合計は 11:06:50)。

### 実装

- 純関数 `challengeTime` (`src/lib/video-challenge-time.ts`) で、同じ練習とみなした組は長い方の 1 本だけ数える (ユーザーの選択: 番号 + 日付)
  - 同じ YouTube の動画 (`youtu.be/ID` と `watch?v=ID` のような URL の書き方違い)。組の代表は番号と日付の読める題名を優先する (題名が URL のままの行があっても、渡す順で結果が変わらない)
  - 題名の練習の番号 (`DAY 7` / `PART7` / `7日目` / `パート7`、全角も) と、題名の日付 (全角も。無ければ投稿日時、それも無ければ行の作成日時の JST 暦日) が**両方とも同じ**動画のうち:

    - **系列が同じ**、または**番号の語までの書き方が同じ** (同じ投稿者の付け方。例「【# # #】絶もうひとつの未来【day #」) なら、題名がまったく同じとき (上げ直し) だけ。同じ投稿者が 1 本目に印を付けずに分割した (「【DAY 7】」と「【DAY 7-2】」) 動画を、別の人の視点と取り違えて消さないため (PR のレビューで検出)
  - ⚠ 日付は前後 1 日を許さない。本番で DAY 1 が「2026 09 18」、PART1 が「2026 09 19」だったのは題名の付け間違いで、ユーザーが題名を直す (2026-10-07)。最初は 1 日を許して組にしたが、Part を毎日 1 から数え直す付け方で隣の日の別の練習を消すと PR のレビューで分かった

- 挑戦時間を出す 6 か所をすべてこの関数に通した (今までは別々に単純な足し算をしていた): 動画タブの「コンテンツ挑戦時間」/「累計練習時間」/「クリアまでの累計時間」、選択モードの「クリアまでの累計時間として保存」、コンテンツ一覧のカード (挑戦時間・クリアまでの時間)、メンテの「クリア日の一括設定」の結果。日付の渡し方 (投稿日時、無ければ行の作成日時) も 4 か所でそろえた

- 動画タブのバッジの hover に「同じ練習の別の動画 N 本は数えていません。長い方の 1 本だけ数えます」を出す (クリア済みの「クリアまでの累計時間」はその範囲での本数)。選択モードで保存するときの確認文にも同じ本数を出す (保存した値は手動入力として自動の値より優先されるので、少ない値と気づかずに保存しないように)

## ⏱ 練習ログ: ログ合計と日ごとの「拘束」で、pull の間の休憩を 1 回 60 分まで数えるようにした (休憩 3 時間の前後でログ合計が約 3 時間跳ねていた・複数日分を 1 本で上げたログで拘束に夜の分まで入っていた)

### 狙い

#447 のレビューで反証された軽い点を、ユーザーの判断で直した (「C は全て修正したい」)。

- ログ合計は「1 本のレポートの中で pull の間が 3 時間以上空いたら区切る」で、休憩が 2 時間 50 分なら全部、3 時間 10 分なら 0 と、3 時間の前後で値が約 3 時間跳ねていた (2 部制の日に起きる)
- 練習ログの日ごとの「拘束」(最初の pull の開始〜最後の pull の終了) は、複数日分を 1 本のレポートで上げると (本番の行の `session_date` はレポートにつき 1 つなので同じ日にまとまる) 夜の分まで入っていた

### 実装

- pull の間の休憩は **1 回 60 分まで**数える (`BREAK_CAP_MS`、ユーザーの選択)。休憩の長さで値が跳ねず、2 部制の日は間の 60 分、複数日分を 1 本で上げたログでも夜の分は 60 分だけ入る
- ログ合計 (`totalLogMs`): レポートごとに「ログの開始 (最初の pull の 30 分前まで) 〜 最初の pull」と「pull + 休憩 (1 回 60 分まで)」を区間にし、和集合の長さを取る。休憩はレポートの中だけで数える (別のレポートとの間はログが動いていなかった時間)。3 時間で区切る `LOG_GAP_SPLIT_MS` はやめた
- 拘束 (`sessionSummary`): 「pull + 休憩 (1 回 60 分まで)」の和集合の長さ。休憩が 60 分より短い日は従来と同じ値。週のまとめのログ合計も同じ関数なので同じ数え方になる
- 区間の和集合 (`unionLengthMs`) と休憩の区間 (`cappedBreakIntervals`) は `fflogs-session.ts` にまとめた (拘束とログ合計で共通)
- 説明 (hover、ja / en) を「pull の間の休憩は 1 回 60 分まで数える」に、拘束の説明も同じ内容に直した。説明の 30 分・60 分と定数の一致は `check-fflogs-progress.mjs` で突き合わせる
- C-4 (コンテンツ一覧の挑戦時間が動画の行を全部読む方式になった件) は、本番で測って今のままにした: 応答の始まりは中央値 254ms で、マクロのページ (194ms) と 60ms ほどの差 (2026-10-07、5 回ずつ)。行が 5,000 を超えたらサーバーのログに残す (`PRACTICE_SECONDS_ROWS_WARN`)

### 検証

- `check-fflogs-progress.mjs`: 夜の分は 60 分だけ・ログの開始は最初の pull の前だけ・60 分以内は全部・60 分を超えたら 60 分・休憩の長さで跳ねない・60 分ちょうどと 61 分・別のレポートとの間は数えない・並び順によらない、説明と定数の一致

## 👥 練習ログ: 同じ夜を 2 人が FFLogs に上げたとき、同じ pull を pull 数・クリア数・ワイプ原因・週のまとめなどで二重に数えないようにした (日の振り返りには両方の行を出し、片方に「別のログと同じ pull (数えない)」と添える)

### 狙い

#447 のレビューで反証された軽い点 C-3。同じ夜を 2 人がそれぞれ FFLogs に上げると、同じ pull が 2 本のレポートに 1 本ずつ入り、pull 数・クリア数・戦闘時間・ワイプ原因・バッジ・週のまとめが二重に数えられる (ログ合計は区間の和集合なので元から 1 回)。本番では今のところ 1 日 1 本のレポートで起きていないが、ユーザーの判断で直した (「C は全て修正したい」)。表示はユーザーの選択「集計だけ 1 本に」: 集計は 1 回だけ数え、日の振り返りには両方のレポートの pull を出す (どちらのログの動画・FFLogs にも飛べるように)。

### 実装

- `src/lib/fflogs-duplicate-pulls.ts` (新規、純モジュール): 別のレポート・同じ encounter・開始と終了の差がどちらも 10 秒以内の pull を同じ pull とみなす。pull の多いレポート (同数ならコードの昇順) を数える側にし、pull ごとではなくレポートの順位で決めるので、同じ夜の数える pull は同じレポートにそろう。3 人が上げたときは 2 本が同じ 1 本を指す。時刻は上げた人の PC の時計なので、時計が 10 秒以上ずれていると同じ pull と分からない (二重に数える。これまで通り)
- `summarize`: 日の pull 数・クリア・ベスト・戦闘時間と合計は数える pull から。日の `fights` には両方の行を残し、`countedFights` と印の表 (`duplicateOf`) を持たせた。数える pull が 0 の日 (2 本のレポートで練習日の付き方が違ったとき) も行は出し、到達度の推移には点を出さない
- 練習ログの画面: 総 pull (DB の数から数えない側を引く)・クリア数 (同じく)・内訳・ワイプ原因・バッジ・層ごとの初討伐・ミス注釈の通し番号・フェーズ滞在時間 (表示中の分とサーバーの全件集計の両方) を数える pull から。ログ合計と動画のオフセットの基準は全 pull のまま (前者は和集合、後者は数えない側のレポートの動画にも要る)
- 日の行: 見出し・死亡数・ワイプ原因・セッションサマリー・プル箱は数える pull から。pull 一覧は全部の行を出し、番号は数える pull だけに振って、数えない側には数える側と同じ番号と「別のログと同じ pull (数えない)」(hover に説明) を付け、破線の枠で薄くした。チャプターのコピーも同じ番号
- 週のまとめ (`summarizeWeek`): 練習日・pull・討伐・ノーデス・節目は数える pull から、ログ合計と戦闘時間は和集合 (数えない側の pull は、数える側がその週にあるものだけ)
- PR のレビュー (6 件) で直したもの:
  - 練習日数のタイルが、別のログと同じ pull だけの日 (2 本で練習日の付き方が違ったとき: 予定に紐づいたログは予定の開催日、0 時過ぎに取り直したログは開始の JST 暦日) も数えていた → 数える pull がある日だけ (到達度の推移・週のまとめと同じ)
  - 週のまとめで、数えない側だけが次の週に入ると、前の週で数えた時間を次の週のログ合計・戦闘時間に足していた → 数える側がその週にある pull だけを渡す
  - 数えない側の pull に付けたミス注釈の hover に通し番号が出なかった → 数える側の番号に読み替える
  - 3 本のログで時計が 0 / +7 / +14 秒とずれると 3 本目を二重に数えた → 重ねた pull とも比べて同じ 1 本に寄せる
  - 数える pull が 0 の日の見出しに層・フェーズの範囲のチップが出ていた → 数える pull から出す。数えない側の hover の文言を、番号が「—」の場合に合わせた
- 対象外 (既知の制約):
  - コンテンツ一覧のスパークラインの pull 数 (hover の文言) と、出欠サマリーの「一部のみ (N/M pull)」の N・M は、DB の関数 (`category_progress_by_day` / `fflogs_report_days`) やレポート単位の合計で数えていて二重になる (出欠の割合は変わらない)。直すには schema の変更が要るのでこの PR では触らない → 次の part で直した
  - 数える側はレポートの pull 数で決め、練習日 (`session_date`) の出どころは見ない。pull の多い方が予定に紐づいていない側だと、その夜の数はそちらの日付に入る
  - 明細が打ち切られている (20,000 件超) と、取得範囲外の古い重複は総 pull・クリア数から引けない

### 検証

- `scripts/check-fflogs-duplicate-pulls.mjs` (新規): 判定 (許容差 10 秒ちょうどと超え・終了の差・encounter 違い・encounter 不明・同じレポートどうし・順位・同数・3 本目・数える側に無い pull・最も近い pull)、`summarize` (数・クリア・戦闘時間・最速・日の行・0 pull の日と推移)、配線 (画面・日の行・pull 行・サーバーのフェーズ滞在時間・週のまとめ・辞書)。`check-logs-weekly-summary.mjs` に「同じ夜のログが 2 本でも pull・討伐・練習日は 1 本分」、`check-video-chapters.mjs` に番号の無い pull のチャプター名を足した
- 9 通りの壊し方 (日・合計を全行で数える・終了を比べない・同じレポートどうしを重ねる・順位を逆・バッジとサマリーを全行に戻す・週のまとめで除かない・推移に 0 pull の日を出す) がすべて検査で落ちることを確認。レビューで直した 4 点 (連なりを追わない・週を日付だけで切る・練習日数を全日で数える・注釈の番号を読み替えない) も、壊すと検査が落ちる (`check-fflogs-duplicate-pulls.mjs` / `check-logs-weekly-summary.mjs` / `check-pull-note-tags.mjs` に追加)

## 👥 コンテンツ一覧・出席サマリー: 同じ夜を 2 人が上げたログの同じ pull を、スパークラインの pull 数と出席サマリーの「一部のみ (N/M pull)」でも二重に数えないようにした

### 狙い

前の part (#453) で対象外にした 2 か所。どちらも DB 側で数えていて、同じ夜を 2 人が上げると pull 数が 2 倍になる。ユーザーの指示で直した (「2をやって」)。

- コンテンツ一覧のカードのスパークライン (`category_progress_by_day`): 日ごとの pull 数 (hover の文言)
- 出席サマリー: 日の pull 数 (M) とメンバーの pull 数 (N)。どちらもレポート単位の合計なので両方 2 倍になり、割合 (「一部のみ」の判定) は変わらないが表示の数が 2 倍だった。2 本目のログにだけ名前が取れなかったメンバーは、割合が半分になって誤って「一部のみ」になり得た

### 実装

- `supabase/schema.sql` 13c-2b (新規): `fflogs_duplicate_pulls(p_from_ms)` が、期間内の pull のうち別のログと同じ pull を返す。条件は練習ログの画面 (`src/lib/fflogs-duplicate-pulls.ts`) と同じ: 同じカテゴリ・別のレポート・同じ encounter・開始と終了の差が 10 秒以内、数える側は pull の多いレポート → コードのバイト順 (`COLLATE "C"`)。「順位が上のレポートに重なる pull があれば数えない」で、TS の「重ねた pull とも比べる」と数えない本数が一致する
  - 速さ: 開始時刻を 10 秒幅の桶に分け、自分と両隣の桶を列にして (`probe AS MATERIALIZED`) 等号の結合で引く。範囲の条件や式のままの結合では、同じカテゴリ・encounter の pull を総当たりにしていた (EXPLAIN で確認、下の検証)
- 13c-3 `category_progress_by_day`: 直近ぶんからこの pull を除く (pull 数・到達区間・残 HP% を 1 回だけ。数える pull が無い日は行が出ない = 練習ログの到達度の推移と同じ)
- 13c-4 `fflogs_report_duplicate_pulls(p_from_ms)` (新規): レポートごとの数。`fflogs_report_days` の戻り値に列を足すと DROP FUNCTION が要るので、別の関数にした
- 15 章: 13c-2b の関数を 13c-3 と同じ配り方にした (公開デモでは anon も)。出席サマリー用に service_role にも付けた。13c-4 の新しい関数は anon から外す
- 出席サマリー (`attendance-summary-actions.ts`): 新しい純関数 `countedAttendancePulls` (`src/lib/schedule/attendance-counted-pulls.ts`)
  - 割り引くのは「重なった相手のレポートが同じ日に数えられている重複」だけ (13c-2b が相手のレポートも返す)。2 夜ぶんを 1 本に入れたレポートが相手のとき、2 夜目の pull を消して「ログなし」にしない
  - メンバーの数は、レポートごとの「数える割合」を掛けて足した値と、どれか 1 本のレポートでの数の大きい方 (日の pull 数で抑える)。出席の行は詳細が取れたレポートにしか無いので、数える側に行が無くても 2 本目の行で数える。居たのに四捨五入で 0 にもならない。重複が無い日は従来と同じ値
  - 重複の数が読めないとき (schema の適用前など) は警告を出して従来の数で出す (出席サマリーごと失敗させない)
- カテゴリの無い pull は、カテゴリの無い pull どうしで比べる (出席サマリーはカテゴリを問わず数えるため)
- PR のレビュー (6 件) で直したもの: 数える側に出席の行が無いと出席が消えた・四捨五入で居た人が 0 になった・2 夜ぶんのレポートが相手だと 2 夜目が「ログなし」になった・カテゴリの無い pull を比べていなかった。残り 2 件 (同じレポートの 2 本が 10 秒以内に並ぶとき・層クラスタの外の戦闘で順位が逆転し 3 本の連なりと重なるとき、TS と DB で数えない本数が 1 本ずれる) は起きるのが稀なので、schema のコメントに書いた

### 検証

- PGlite で、実際の `schema.sql` から 3 つの関数を切り出して実行し、TS の `duplicatePulls` と突き合わせた: 乱数で作った夜 (1〜3 本のログ・時計のずれの連なり・録り始めの遅れ・0 時過ぎの取り直しで日付違い・2 カテゴリ) 25 夜 × 5 通りで、数えない pull の集合 (計 810 本)・レポートごとの数・スパークラインの日ごとの pull 数がすべて一致し、返す相手のレポートはすべて 10 秒以内に重なる pull を持つ。カテゴリの無い pull どうし・期間の境目も確認。直す前の schema ではスパークラインが重複込みで数えることも確認
- 速さ (PGlite): 本番に近い 4,800 行でスパークラインは 23ms → 31ms、4 万行で 126ms → 147ms (レビュー対応後。レビューの実測では 8.6 万行・365 日で 5,310ms → 1,847ms と速くなる)。最初の書き方では 4 万行で 1,001ms (桶が結合のキーに入らず 62 万行を読み捨てていた) だったので、EXPLAIN を見て直した
- `scripts/check-attendance-counted-pulls.mjs` (新規): 割り戻し (重複なし・丸ごと同じ・一部だけ・日の数を超えない・負にしない) と配線 (読めなくても止めない)。`check-fflogs-duplicate-pulls.mjs` に DB 側の条件が TS の定数と同じか (許容差・桶の幅・順位・権限) を足した
- 7 通りの壊し方 (スパークラインで除かない・順位を逆・終了の差を見ない・メンバー / 日の数を割り戻さない・読めないと失敗させる・anon に配る) がすべて検査で落ちることを確認。レビュー対応後の 6 通り (相手の日を見ない・1 本のレポートでの数を下限にしない・割り戻さない・相手のレポートを渡さない・相手を順位の上から選ばない・相手ごとに分けない) も落ちる
- `check-attendance-counted-pulls.mjs` に、レビューで出た場面 (数える側に出席の行が無い・一部だけ重なる・四捨五入で 0・2 夜ぶんのレポートが相手・相手が期間の外) を足した

## 🔒 セキュリティ: データベースの規則でも、Discord サーバーのメンバーと確認できた人だけが読み書きできるようにした (書き込みは確認から 72 時間以内。サーバーを抜けた人・ロールを外された人の権限は、次にサイトを開いたときかログインし直したときに閉じる)

### 狙い

2026-10-07 のセキュリティ精査で、Discord サーバーのメンバー確認がアプリの画面側 (ログイン処理と proxy) にしか無く、データベースの規則 (RLS) は「ログイン済みのトークンを持っていること」と、トークンの中の admin の印しか見ていないと分かった。サーバーのメンバーでない人がデータベースに届く経路と、サーバーを抜けた人・ロールを外された人の権限がデータベース側で残る経路があった。

### 実装

- `supabase/schema.sql` 1 章: 判定の関数を 3 つ追加
  - `is_portal_member()` (読み取り): メンバーの印 (`discord_guild_member` と `discord_id`) がある。サーバー外の人は印を持たない
  - `is_portal_verified_member()` (書き込み): それに加えて、最後にサーバーを確かめた時刻 (`discord_member_verified_at`) が 72 時間以内。壊れた値は false
  - `is_portal_admin()`: 確認済みのメンバーで admin
- 読み取りのポリシー (本番) は `is_portal_member`、書き込み (出欠・日付メモの本人) は `is_portal_verified_member`、admin の書き込み (ループ・ブロックリスト・Storage・予定の時刻の一括更新の関数) は `is_portal_admin` に通す。公開デモの匿名の読み取りは従来どおり
- 読み取りに鮮度を求めない理由 (PR のレビューで検出): ブラウザの supabase-js はトークンを Supabase Auth から直接取り直すので、開いたままのタブでは確認の時刻が更新されない。読み取りに鮮度を求めると、しばらくサイトへのリクエストが無かったタブの再取得がエラーにならず 0 行になり、画面が黙って空になる
- アプリ: サーバーにいないと確定したとき (proxy の定期の確認・ログイン処理) に、メンバーと admin の印を false に書き戻す (`markGuildMembershipRevoked`)。Discord の一時障害では書き戻さない
- アプリの確認の間隔を DB の 72 時間と食い違わないよう抑えた (env で長くしても hard TTL は 72 時間・soft TTL は 24 時間まで)。確かめ直した後の `refreshSession` の失敗を記録する
- CI: 本番の schema 適用のあとに「メンバー確認を通らない authenticated 向けのポリシーが 0 本」を表明する。TO 句の無いポリシー (public 向け) も数える (anon の表明も同じく)
- `docs/setup.md`: 使わない Email のログインを OFF にする手順を足した
- 残るもの: サーバーを抜けた人は、サイトを開かないまま手元のトークンを取り直し続けると、読み取りは続けられる (次にサイトを開いた時点で閉じる)。書き込みは最後の確認から 72 時間で閉じる

### 検証

- 実際の `schema.sql` から関数とポリシーを切り出して PGlite で実行した (ロール別のトークンで読み書き)。直す前の schema では、メンバーの印の無いトークンが全行を読め、確認から 30 日たった admin のトークンが全行を消せた。直した後は、印の無い・失効したトークンは読み書きできず、確認から 73 時間・30 日のトークンは読めるが書けない。メンバー (確認 1 時間前・71 時間前) と admin は従来どおり読み書きでき、公開デモの匿名ゲストは従来どおり読める。旧版の規則が入った DB に流しても、2 回流しても同じ結果。CI の表明の問い合わせは 0 本を返し、TO 句の無いポリシーを足すと拾う
- `scripts/check-rls-membership.mjs` (新規): 判定の関数・アプリの TTL の上限・全ポリシー・失効の書き戻し・CI の表明。14 通りの壊し方がすべて検査で落ち、データベースの挙動に関わる 6 通りは PGlite の実行でも落ちる
- PR のレビュー (5 件) で、開いたままのタブで画面が空になる経路・env の TTL との食い違い・CI の表明が public 向けを見逃す・refreshSession の失敗・書き方が強すぎる、を直した
- schema 全体を Postgres の構文解析 (pglast) に通した
