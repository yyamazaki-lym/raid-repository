## ☠ 練習ログ: 各 pull に「ワイプ原因」— 最初に落ちたジョブと致命の技

調査ノート第 4 回 (`docs/ff14-tools-research-2026-09-06-wide.md`) の **W-1** です。

**狙い**: 練習ログには pull ごとの残 HP% と死亡数はありましたが、「何で止まったか」が無く、振り返りは FFLogs の Deaths タブを開くところから始まっていました。FFLogs の Summary table (既に PT 合計 DPS / 死亡数の取得で読んでいる) には `deathEvents` (誰が・いつ・何の技で倒れたか) が入っているので、そこから **最初の死亡** を pull 行に添えます。

**表示**: pull 行の末尾に `☠ PLD ← アク・モーン +1` の形のチップ (最初に落ちたジョブの略称 ← 致命の一撃の技名、+N = 10 秒以内に続けて落ちた人数)。hover で時刻・フェーズ・死亡総数。日を開くと「ワイプ原因: 技名 ×N」の 1 行、上部には「ワイプ原因」カード (コンテンツ全体で初死亡の技を多い順、絶では初死亡が起きたフェーズの回数も) を追加しました。データが 1 つも無いコンテンツではカードも行も出ません。

**保存するもの / しないもの**: `fflogs_fights.death_events` (jsonb) に `{ t, job, ability }` の配列を保存します。**プレイヤー名は保存しません** — 練習ログの設計原則 (個人を序列化して表示しない) の延長で、粒度はジョブ略称までです。10 秒のクラスタ窓は Wipefest (WoW) の「最初の死亡クラスタだけを原因として採用し、ワイプコール後の巻き添えは除く」考え方を借りました。致命の一撃 (killing blow) は DoT や遅れて倒れた場合に真因と一致しないことがあるので、カードの注記にその旨を書いています。

**実装**: 純関数を `src/lib/fflogs-fight-detail.ts` に分離 (`extractDeathEvents` / `summarizeWipe` / `wipeCauseCounts` 等)、同期側 `src/lib/server/fflogs-fights.ts` の `parseSummaryTable` に fight の開始/終了時刻を渡して `deathTime` (レポート相対 ms) を pull 相対に直して保存、読み出し側 `src/lib/supabase/fflogs-fights.ts` で `FightRow.wipe` に要約を付けます。既存の同期で取れた pull は次回の同期 (直近 14 日は再取得される) で埋まります。

**検証**: `node scripts/check-fflogs-fight-detail.mjs` (時刻正規化 / 抽出 / 要約 / 集計 / 書式の 30 項目)、`tsc --noEmit`、`eslint`、`next build`。実 API には本環境から到達できないため、フィールド名は v2 スキーマダンプと Better Deaths / xivodreview の実装で確認した形に合わせています。

**動作影響**: 同期の API 往復数は増えません (Summary table は既に取っていた)。1 pull あたりの RSC payload は死亡要約分 (数十バイト) だけ増えます。

## ⏱ 練習ログ: 絶のフェーズ滞在時間 (pull ごとのバーと合計)

調査ノート第 4 回の **W-2** です。

**狙い**: 絶では「P3 に何分費やしたか」が練習の重心そのものですが、これまでは到達フェーズ (`lastPhase`) しか持っておらず、各 pull の中でどのフェーズにどれだけ居たかは分かりませんでした。FFLogs v2 の `fights.phaseTransitions { id startTime }` (観測されたフェーズ遷移の時刻列) を取り込み、pull ごとの滞在区間にします。

**表示**: 絶 (フェーズ管理コンテンツ) の pull 行で、P チップの隣に幅 4rem の帯 (フェーズごとの滞在割合、色はフェーズの識別色と同じ) を出し、hover で各フェーズの秒数。上部には「フェーズ滞在時間」カード (全 pull 合計の積み上げバー + 割合 + 時間) を追加しました。零式は表示しません (フェーズ表記は絶のみ、という 2026-08-28 の判断のまま)。遷移が取れていない pull は帯の幅だけ残して縦揃えを保ちます。

**実装**: fights クエリを「phaseTransitions 付き → 従来の full → minimal」の 3 段 fallback にし、FFLogs 側でフィールドが消えても取り込み全体は止まらないようにしました。保存は `fflogs_fights.phase_transitions` (jsonb、`{ id, t }` の配列、t は pull 相対 ms)。PostgREST の一括 upsert が全行同じキー集合を要求するため、列を送るかはレポート単位で決めています。読み出しでは `includePhases` (絶のみ true) のときだけ `FightRow.phases` に区間を載せ、零式の payload を増やしません。開始フェーズが遷移として含まれない場合は 0 秒開始で補い、同時刻の重複遷移は畳みます。

**検証**: 上と同じスクリプト (正規化 / 区間 / 合計の項目)。`supabase/schema.sql` に 2 列 + jsonb 型の CHECK (NOT VALID) を追加、main へ merge されると deploy-database ワークフローで反映されます。

## ⏰ 出欠: 遅刻・早退の予定時刻を入れられるように (確定通知にも反映)

調査ノート第 4 回の **W-13** です。

**狙い**: 国内の固定で最も揉めるのは「遅刻」で、掲示板・知恵袋でも「5 分遅刻が常態」「事前連絡があれば可」が繰り返し議論されています。○×△ (と ⏰) の記号だけでは「出るが 21:30 になる」「23:00 で抜ける」が表現できず、結局 Discord のチャットで個別に伝える運用でした。Raid-Helper の Late / Tentative や、国内の xivraidteam シートの「開始可能時刻」入力を参考に、**記号はそのまま、到着予定 / 早退予定の HH:MM を出欠行に添える**形にしました (凡例マスターは admin が自由に編集できるので、記号の意味を portal 側で固定しない)。

**表示 / 操作**: 自前作成式の出欠 popover に「遅刻 / 早退の予定 (任意)」として 2 つの time 入力 (到着 / 早退) を追加。○ / △ / ⏰ など「出る」記号を選んでいるときだけ入力でき、欄の外を押した時に保存します (時 → 分と入力する途中で保存が走らないように)。× と未回答では保存しません (server 側でも null に落とす)。出欠表では記号の横に `21:30〜` / `〜23:00` / `21:30〜23:00` を 9px で添え (他人のセルは title に「到着予定 21:30」)、Discord の確定通知では出欠ブロックの名前の横に `(21:30〜)` として出ます。

**保存**: `native_schedule_attendances.arrive_at` / `leave_at` (text、HH:MM)。本人が PostgREST を直接叩いて書ける列なので、symbol / comment と同じ方針で DB 層にも形式 CHECK (`^([01][0-9]|2[0-3]):[0-5][0-9]$`、NOT VALID) を置きました。形式が固定なので通知本文への注入面にはなりません。自動確定の「参加可能人数」判定は変えていません (遅刻・早退は参加可能側のまま)。

**実装**: 純関数を `src/lib/schedule/attendance-times.ts` に分離 (`normalizeAttendanceTime` / `formatAttendanceTimesHint` / `describeAttendanceTimes` / `symbolAllowsTimes`)。`ScheduleSession.attendanceTimes` (optional、native のみ) を `native-fetch.ts` が埋め、`schedule-list.tsx` のセルと `native-attendance-popover.tsx` が読みます。同期式 (character-sheets) には無い概念なので、sync 経路の型・表示は変わりません。

**検証**: `node scripts/check-attendance-times.mjs`、`tsc --noEmit`、`eslint`、`next build`。

## 🕒 Discord 通知に相対時刻 (N 時間後) / 次回開催カードに開始までのカウントダウン

調査ノート第 4 回の **W-14** です。

**Discord 側**: Discord のタイムスタンプ表記 `<t:unix:F>` / `<t:unix:R>` は、読む人のタイムゾーンとロケールで「9月8日(火) 21:00」「3 時間後」に描画されます (Discord API docs の Timestamp Styles で確認)。開催確定通知と出欠催促のテンプレートに `{discord_time}` / `{discord_relative}` の placeholder を追加し、既定の確定通知では 🕘 行を `21:00 〜 23:00 (3 時間後)` の形にしました (既定テンプレートは括弧付きの `{discord_relative_block}` を使い、日付が読めないときは括弧ごと省略されます — `{note_block}` と同じ型)。開始時刻は `raw_date` の日付部分 (`YYYY/MM/DD`) + 開始 HH:MM を JST として UNIX 秒に直します (`sessionStartUnixSeconds`)。解釈できない日付では placeholder は空文字になり、行末の空白は落とします。設定ダイアログの placeholder 一覧にも追記しました。催促の既定テンプレートは変えていません (placeholder を使える状態にしただけ)。

**Web 側**: 次回開催カードはサーバー描画のスナップショットで「本日 / 明日 / あと N 日」までしか出せなかったので、`SessionCountdown` (client) を足し、本日で開始前なら「開始まで 1 時間 32 分」を 30 秒ごとに更新して出します。開始後は従来の「挑戦中」表記がそのまま担います。現在時刻は `useSyncExternalStore` の外部ストア (サーバースナップショットは 0 = 描かない) で読み、effect 内 setState を使いません (hydration 差分も出ません)。

**動作影響**: テンプレートを自分で書いている固定では、新しい placeholder を書き足すまで表示は変わりません。既定テンプレートを使っている固定は 🕘 行に相対時刻が付きます。

## 🎨 「良い / 注意 / 悪い」の色を 5 段階のスケールに統一 (残 HP%・死亡数・出欠・消化チェック)

調査ノート第 4 回の **UI-12** です (他ゲームのツール比較で WoWAudit の 3 色、WoWAnalyzer の `colorForPerformance` 5 段階が「全画面で同じ意味色」を持っていたことから)。

**経緯**: portal 内の意味色は画面ごとに別体系でした。残 HP% は「討伐に近いほど暖色」の熱量色 (rose = 0% 寸前 = 良い)、死亡数・ワイプ原因は rose = 悪い、出欠は ○ がテーマ色 (cyan)・△ が violet・× が rose、消化チェックは消化済 = emerald・辞退 = amber。同じ rose が「もう少しで討伐」と「死亡」の両方を指していました。

**変更**: `src/lib/perf-tone.ts` に 5 段階 + neutral のスケール (**良い = emerald → lime → amber → orange → rose = 悪い**) と、値 → 段階の関数 (`perfForRemainingPercent` / `perfForRatio` / `perfForProgress` / `perfForDeaths`) を置き、次を乗せ換えました。

- 練習ログ: 残 HP% の文字色 (`percentageToneClass`。討伐 = emerald、≤10% = lime、≤30% = amber、≤60% = orange、それ以上 = rose。2% 未満の区別は小数 2 桁の数値に任せる)、pull 行の死亡数 (0 = 良い … 5 以上 = 悪い)、日ごとの到達度バーの塗り (到達度の段階色。記録更新日は濃く、それ以外は薄く — 旧 cyan 濃淡の役割を引き継ぐ)、ワイプ原因チップとカードのバー (= 悪い)
- 出欠 (`ATT_TONE`): ○ / ◯ = 良い、⏰ 遅刻 = やや良い、△ 未定 = ふつう、× = 悪い、－ = neutral。凡例も同じ辞書を読むので自動で揃います
- 今週の消化チェック: 消化済 = 良い、辞退 = ふつう、未消化 = neutral、「未消化 N 名」バッジは 0 名 = 良い / 残りあり = 注意。BiS の「部位 n/11」は充足率の段階色

**変えていないもの**: 層・フェーズの識別色 (sky → teal → violet …) は「どれか」を表すカテゴリ色なので対象外。コンテンツのステータスバッジ (未着手 / 練習中 / クリア済 / 休止中) は既にトークン化された信号色で意味が一致しているため触っていません。軽減カードの「素ダメ = rose / 軽減率 = sky / 最終 = emerald」は列の種別色で良し悪しではないので対象外。エラー表示 (rose) と削除ボタン (rose) は従来どおり。

**原則**: 色だけで意味を伝えない (WCAG 1.4.1) — 数値・記号・ラベルは全箇所で併記済み。7 テーマ共通の固定色 (テーマの accent は選択中 / リンクの役割に専念)。

**最も見え方が変わる箇所**: 出欠表の ○ (cyan → emerald) と △ (violet → amber)、練習ログの残 HP% (熱量色 → 良し悪し色)。いずれも `perf-tone.ts` の辞書 1 か所で調整できます。

**検証**: `node scripts/check-perf-tone.mjs`、`tsc --noEmit`、`eslint`、`next build`。

## 🈶 練習ログ: ワイプ原因の技名を日本語で表示 (既存の pull も次の同期から順に置き換わる)

FFLogs の Summary table が返す致命技の名前 (`ability.name`) は英語で、「ワイプ原因」カードと各 pull のチップがそのまま英語 (Unmitigated Explosion など) になっていました。同じ要素に付いているゲーム内 action ID (`ability.guid`) をキーに、同期時に [XIVAPI v2](https://v2.xivapi.com/) の `Action` シート (`?rows=…&fields=Name&language=ja`) から日本語名を引いて `death_events[].ja` に保存します (`src/lib/xivapi-actions.ts` = 純関数 / `src/lib/server/xivapi-action-names.ts` = fetch + プロセス内 7 日キャッシュ)。表示と集計 (`summarizeWipe` / `wipeCauseCounts`) は日本語名を優先し、無ければ従来の英語名に戻ります。

- 名前が既に非 ASCII (アップロード者の言語で翻訳済み) の技、ID の無い死亡 (DoT 等) は引きません。XIVAPI に届かない / 見つからないときは英語のままで、同期そのものは失敗しません (取得は FFLogs の後段で、同期の時間予算を共有)。
- **既存分の置き換え**: この変更より前 (`2026-09-06 12:00 JST` 以前) に同期したレポートは、次の同期で 1 回だけ取り直します (新しいレポートが優先されるのは従来どおり。件数が 1 回の枠を超えても数回の同期で消化されます)。取り直しは FFLogs の同じクエリを使うので、ポイント消費は初回同期と同じです。
- 保存形の変更は jsonb 要素へのキー追加 (`id` / `ja`) のみで、schema.sql の変更はありません。

**検証**: `scripts/check-fflogs-fight-detail.mjs` に guid の抽出 / 日本語優先の表示 4 ケース、`scripts/check-xivapi-actions.mjs` (新規) に URL 組み立て / 応答パース / 引くべき ID の選別 / 書き戻しの 12 ケース。XIVAPI と FFLogs 実 API には本環境から到達できないため、応答の形は v2 の公開仕様 (`rows[].row_id` / `rows[].fields.Name`) に対する契約検証です。

**仕組み**: `src/lib/i18n/` に辞書 (`messages.ts`、日本語を正として英語は同じ形を型で強制) / cookie を読む `getLocale()` (Server Component、React.cache) / client 向け `LocaleProvider` + `useMessages()` / cookie を書く Server Action `setLocaleAction`。root layout が cookie を 1 回読んで `lang` と Provider を決め、各コンポーネントは Server なら `getMessages()`、Client なら `useMessages()` で同じ辞書を引きます。切替は Server Action で cookie を書いた後に `router.refresh()`。外部ライブラリは使っていません (URL プレフィックス型の i18n ルーティングを持ち込まないため)。純関数 (`formatCountdown` / `describeAttendanceTimes`) は `locale` 引数を任意で受け、既定は従来どおり日本語。

**検証**: `tsc` / `eslint` / `check-changelog` / `check-attendance-times` 通過、`next build` 成功。`/login` を cookie 無し (日本語) と `rr_locale=en` (English) で描画確認。
