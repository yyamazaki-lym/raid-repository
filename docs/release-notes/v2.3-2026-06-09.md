## 🛡️ PR — Discord 画像 migrate の SSRF 強化 + cron error body 整理 + first_clear 系 action に admin gate + sort_order 計算を Postgres RPC 化

**経緯**: 全体監査の Medium / Low 4 件を 1 PR にまとめて処理 (#7 discord-image-migrate / #8 cron error body / #14 first_clear admin gate / #10 sort_order race)。

**(1) Discord 画像 migrate の SSRF 強化 (#7)** [src/lib/server/discord-image-migrate.ts](src/lib/server/discord-image-migrate.ts): 旧実装は `redirect: "follow"` で 3xx を自動追従しており、Discord CDN が万一内部 IP に飛ばす redirect を返した場合の SSRF 余地が浅かった。`redirect: "manual"` に切り替え、各 hop の Location を `isDiscordCdnUrl` で再判定して最大 2 hop だけ手動で follow (Discord CDN ホスト以外は遮断)。さらに `arrayBuffer()` だと Content-Length を偽った 5MB 超のレスポンスを全部メモリに乗せてから判定していたのを、`res.body.getReader()` で chunked 読み取りして上限到達で `reader.cancel()` する `readBodyWithLimit` ヘルパに差し替え。

**(2) cron error body のレスポンス露出を整理 (#8)** [src/lib/server/discord-import.ts](src/lib/server/discord-import.ts): `runDiscordImport` の Discord API エラー時、これまで `res.text().slice(0, 200)` を `ImportResult.reason` にそのまま入れて cron response JSON に流していたが、Vercel ログ画面共有時にトークン断片 / rate-limit メッセージが残るリスクがあった。`reason` は `discord api ${status} (page N)` の構造化メッセージのみにして、詳細 body は `console.warn` にだけ吐く。

**(3) first_clear 系 Server Action に admin gate (#14)** [src/lib/server/categories-actions.ts](src/lib/server/categories-actions.ts): `maybeSetFirstClearAtAction` / `backfillFirstClearFromExistingVideos` は元々 admin gate 無し (= RLS 任せ) で、Critical PR で `userIsAdmin` を fail-closed 化した結果、非 admin が呼ぶと RLS UPDATE が空振りして UI 上「成功っぽく返ったが何も起きない」状態になり混乱を招いていた。両 action 冒頭で `await assertAdminResult()` を呼んで明示的に 403 を返すよう変更。

**(4) sort_order 計算を Postgres RPC に寄せる (#10)** [supabase/schema.sql](supabase/schema.sql) / [src/lib/server/categories-actions.ts](src/lib/server/categories-actions.ts) / [src/lib/server/discord-import.ts](src/lib/server/discord-import.ts): `SELECT max(sort_order) → +1 → INSERT` の JS 側 TOCTOU を縮める。新規 SQL 関数 `next_category_sort_order()` と `next_category_link_sort_order(category_id, kind)` を SECURITY DEFINER で追加 (anon, authenticated に EXECUTE GRANT)。`createCategoryAction` / `createCategoryLinkAction` / `discord-import.ts` の `importChannel` 3 箇所を `supabase.rpc(...)` 呼び出しに置換。RPC と INSERT 間の race window は残るが (完全な atomic ではない)、JS 側 SELECT を踏むより 1 round-trip 短く、RLS の影響も受けない。

**触らない範囲**: Critical PR で扱った fflogs / page-title / DISCORD_ADMIN_ROLE_IDS / app_settings 周りは無関係 (本 PR はそれ以外の Medium / Low をまとめている)。`bigserial` 化 / UNIQUE 制約の追加 (= race の完全排除) は既存データの整合性確認が必要なので別 PR 候補に残す。

**検証**: dev 環境で (a) Discord で生きた CDN URL を kind='image' で追加 → 通常通り Storage に migrate される / 期限切れ URL → 403 で reason 表示、(b) cron import-discord を `DISCORD_BOT_TOKEN=invalid` で叩いて response JSON が `discord api 401 (page 1)` のみで body が混入していないこと + Vercel logs に詳細 warn、(c) 非 admin で `backfillFirstClearFromExistingVideos` を呼ぶと `{ ok: false, reason: 'ADMIN ロールが必要です' }`、(d) categories / category_links の新規作成で `sort_order` が連番で振られる、を確認。

## 📝 PR — fflogs OAuth error の URL echo をスリム化 + 全 cron スケジュール表を cron-auth.ts に集約 (Low 2 件)

**経緯**: 全体監査の Low 2 件 (#12 / #13) を雑事まとめ PR として処理。

**(1) fflogs OAuth token 交換失敗時の reason 文字列をスリム化 (#12)** [src/lib/server/fflogs-oauth.ts](src/lib/server/fflogs-oauth.ts:170-180): `reason: 'token 交換失敗 (${res.status}): ${text.slice(0, 200)}'` だった文言を `'token 交換失敗 (HTTP ${res.status}) — Vercel ログで詳細を確認してください'` に短縮し、詳細 body は `console.warn` にのみ吐く。これで `?fflogs_oauth_error=...` query で URL に長文 / 制御文字 / token 様文字列が echo されなくなる。React 経由 render なので XSS にはならなかったが、UX とログ汚染の改善。

**(2) 全 cron スケジュール表を cron-auth.ts に集約 (#13)** [src/lib/server/cron-auth.ts](src/lib/server/cron-auth.ts): JSDoc に `route × schedule(UTC) × JST × 発火元 (Vercel/pg_cron) × 設定ファイル` のテーブルを 1 表で書き込む。3 cron route が import するファイルなので IDE の Go-to で必ずたどり着け、運用時に「今何時に何が発火するか」を別ドキュメントを当たらず確認できる。

**触らない範囲**: コードロジックの変更なし。changelog 整理目的の 1 行コミット相当の改修。残る Low #15 (callback signOut on failure) / #16 (CSP 'unsafe-inline') は現状維持で OK と punch list で判定済。Medium #6 (Vercel KV / Upstash Redis 化) は Vercel Marketplace の integration セットアップ (ユーザー手動操作) が必要なので別 PR で扱う。

## 🔧 PR — cron 認証ヘルパ抽出 + 全 cron route の maxDuration を 60s → 300s に統一

**経緯**: 直近の全体監査で「3 つの cron route ([import-discord](src/app/api/cron/import-discord/route.ts), [snapshot-schedule](src/app/api/cron/snapshot-schedule/route.ts), [notify-native-schedule](src/app/api/cron/notify-native-schedule/route.ts)) が `CRON_SECRET trim → Authorization: Bearer 比較 → x-vercel-cron 確認` をそれぞれ独立に書いており、1 箇所だけ check 抜け / typo を入れてもレビューで見落としやすい」と「`maxDuration = 60` だと Discord import (N カテゴリ並列 × 5 ページ pagination × 15s timeout × per-URL enrichment) が 60s を超えうる」の 2 件 (Medium #11 / #9) を 1 PR にまとめて解消。

**変更内容**:
- **新規** [src/lib/server/cron-auth.ts](src/lib/server/cron-auth.ts): `assertCronAuth(req, routeLabel): NextResponse | null` を切り出し。検証ロジックを 1 ファイルに集約し、各 route は戻り値を early return するだけ。response body には詳細を載せず長さ / prefix だけ console.warn に吐く (Vercel ログ画面共有時の漏洩リスク軽減)
- **編集** [src/app/api/cron/import-discord/route.ts](src/app/api/cron/import-discord/route.ts) / [snapshot-schedule/route.ts](src/app/api/cron/snapshot-schedule/route.ts) / [notify-native-schedule/route.ts](src/app/api/cron/notify-native-schedule/route.ts): 各 route の auth ブロックを `const denied = assertCronAuth(req, '<label>'); if (denied) return denied;` に置換。`maxDuration` を 60 → 300 に引き上げ (Vercel Functions 標準 default の 300s に揃える、Vercel Hobby/Pro 共通で許容)

**触らない範囲**: Vercel cron の発火 path / `vercel.json` の schedule / 各 cron が呼ぶ shared function (`runDiscordImport` / `runScheduleSnapshot` / `dispatchNoonNotifyForToday`) 本体ロジック。Supabase pg_cron 経由の `notify-native-schedule-hourly` も `Authorization: Bearer ${CRON_SECRET}` ヘッダを送る形式は変わらないので無改修で通過する。

**検証**: dev 環境で `curl http://localhost:3000/api/cron/import-discord` (Authorization なし) → 401 / `curl -H 'Authorization: Bearer wrong' .../import-discord` → 401 / `curl -H 'Authorization: Bearer $CRON_SECRET' .../import-discord` → 200 + 結果 JSON、を 3 route 全部で同じ挙動を確認。本番では Vercel Dashboard → Cron Jobs から手動 trigger で正常完了することを確認。

## 🔒 PR — セキュリティ Critical 5 件まとめ修正 (fflogs route admin gate / OAuth state を cookie 化 / page-title SSRF + rate limit / app_settings 平文 fallback 撤去 / DISCORD_ADMIN_ROLE_IDS fail-closed 化)

**経緯**: 全体監査で「運用上踏みうる」セキュリティ系の穴 5 件が見つかったため、後続レビュー (Medium / Low) に影響を出さないよう Critical だけを 1 PR にまとめて投入する。書き込み系は二重ゲート (Server Action + RLS) で守られていたが、入口側 (Route Handler / SSRF / fallback) に穴が残っていた。

**(1) fflogs route 3 つに admin gate を追加** [start/route.ts](src/app/api/auth/fflogs/start/route.ts) / [callback/route.ts](src/app/api/auth/fflogs/callback/route.ts) / [disconnect/route.ts](src/app/api/auth/fflogs/disconnect/route.ts): proxy.ts は guild membership だけチェックして通すので、非 admin guild メンバーが任意に OAuth start / disconnect を叩けていた。Route Handler は Server Action と違い next-action ヘッダによる自動 CSRF 防御が無いため、認可レベルで遮断する。各 route 冒頭に `await assertAdminResult()` を入れ、非 admin は start/callback は `/auth/denied?reason=not_admin` redirect、disconnect は 403 JSON。

**(2) FFLogs OAuth state を `app_settings` のグローバル単一行 → HttpOnly cookie に移行** [fflogs-oauth.ts](src/lib/server/fflogs-oauth.ts) / [start/route.ts](src/app/api/auth/fflogs/start/route.ts) / [callback/route.ts](src/app/api/auth/fflogs/callback/route.ts): 旧設計は `app_settings.fflogs_oauth_state_pending` の 1 行を全ユーザーで共有しており (a) admin 2 名が同時に OAuth を始めると先発の state が消えて callback が `state mismatch` で失敗、(b) anon SELECT が全テーブル開いている (USING (true)) ため browser から state を読めて CSRF 防御の前提が崩れる、の 2 問題があった。`buildAuthorizeUrl` から DB upsert を削除して state を返すだけにし、`/start` 側で `cookies.set('fflogs_oauth_state', state, { httpOnly, secure, sameSite: lax, maxAge: 600 })`、`/callback` 側で cookie 値と URL `?state=` を比較して `maxAge: 0` で消す形に再構成。`exchangeCodeForTokens` の引数からも state を除去。

**(3) `/api/page-title` に SSRF / body-size / rate-limit ガード** [url-safe.ts](src/lib/url-safe.ts) (`isPublicHttpUrl` 追加) / [src/app/api/page-title/route.ts](src/app/api/page-title/route.ts) / [src/lib/server/page-title.ts](src/lib/server/page-title.ts) / [src/proxy.ts](src/proxy.ts): `isSafeUrl` は http(s) スキームしか見ていなかったため、認証済ユーザー (および PUBLIC_DEMO_MODE の匿名読者) から `http://10.0.0.1/` / `http://127.0.0.1/` / `http://169.254.169.254/` (AWS IMDS) などへ server-side fetch できる SSRF 経路だった。さらに `res.text()` の前段で `Content-Length` チェックが無く、巨大 HTML を返すサイトを指せば Vercel 関数のメモリ / active CPU 課金を食い潰せる + rate limit 対象外だった。新規 `isPublicHttpUrl(raw)` で IPv4 リテラル (loopback/private/CGNAT/link-local/multicast) + IPv6 (`::1`/`fc..`/`fd..`/`fe80::`) + ホスト名 (localhost/.local/.internal/.localhost) を弾き、route 入口と `fetchPageMeta` 双方で使用。fetch を `redirect: "manual"` に切替えて 3xx 時に Location ヘッダを再度 `isPublicHttpUrl` で検証して 1 段だけ手動 follow、最大 3 hop。HTML body は `res.body.getReader()` で chunked 読み取りして 1MB 上限到達で `reader.cancel()`。proxy.ts の `RATE_LIMIT_RULES` に `{ scope: 'api-page-title', limit: 30, windowMs: 60_000 }` を追加。検証中に `URL.hostname` が IPv6 リテラルを `[::1]` (角括弧付き) で返すことが発覚し、bracket を剥がしてから比較する 1 行 fix を追加 (これがないと `[::1]` / `[fe80::1]` / `[fc00::1]` が通過してしまっていた)。

**(4) FFLogs token の `app_settings` 平文 fallback を撤去** [fflogs-oauth.ts](src/lib/server/fflogs-oauth.ts) / [categories-actions.ts](src/lib/server/categories-actions.ts) / [supabase/schema.sql](supabase/schema.sql): `SECRET_ENCRYPTION_KEY` 未設定 / `SUPABASE_SERVICE_ROLE_KEY` 未設定の fork で `persistTokens` が `app_settings` (平文) に access_token / refresh_token を書く graceful degrade パスがあったが、anon SELECT が開いているため平文 token が browser から覗ける状態だった。`persistTokens` から fallback 分岐を削除して `{ ok: false, reason }` を返し、`exchangeCodeForTokens` / `refreshTokens` で propagate (callback で `?fflogs_oauth_error=...` 表示)。`getValidFflogsOAuthToken` / `getFflogsOAuthStatus` / `getFflogsSessionCookieStatus` の `fetchAppSetting(KEY_ACCESS/REFRESH)` fallback も全削除し `getSecretValue` のみ参照。schema.sql 末尾に過去に書かれた legacy plaintext を一掃する idempotent DELETE (`fflogs_oauth_access_token` / `fflogs_oauth_refresh_token` / `fflogs_session_cookie` / `fflogs_oauth_state_pending`) を追加。**注意**: この変更で `SECRET_ENCRYPTION_KEY` 未設定の本番環境では FFLogs 連携が動かなくなる — 既存 fork は env を設定してから再連携が必要。

**(5) `userIsAdmin([])` を fail-open → fail-closed に反転** [auth.ts](src/lib/server/auth.ts): `getAdminRoleIds()` が空配列 (= `DISCORD_ADMIN_ROLE_IDS` env 未設定) のとき `userIsAdmin([])` は `true` を返す後方互換挙動だったが、fork が env を設定し忘れた瞬間に全 guild メンバーが admin になり anon key + JWT で REST 直叩きから RLS write が通過してしまうリスクがあった。`adminIds.length === 0` を `false` に反転。dev 環境で env なしでも admin 視点を再現できるよう `DEV_BYPASS_ADMIN_ROLE_ID = '__dev-bypass-admin__'` 定数を新設し、`devAuthBypassUser()` がこの固定 ID を roles に入れる + `userIsAdmin` がこの ID を見て常に true を返す特例を組み込む (production ビルドでは devAuthBypassUser が null を返すため非到達)。

**触らない範囲**: 後続 PR で扱う予定の Medium / Low (rate-limit を Upstash Redis 化 / cron auth helper 抽出 / cron maxDuration 上げ / discord-image-migrate の redirect=manual / sort_order race / `maybeSetFirstClearAtAction` の admin gate 整合 / `app_settings` の anon SELECT を policy で絞る) は本 PR では触らない。`secret-cipher.ts` の AES-256-GCM 実装は無傷。

**検証**: dev preview で (a) `DEV_AUTH_BYPASS=true` + `DEV_AUTH_BYPASS_NON_ADMIN=true` (= 非 admin 視点) で `/api/auth/fflogs/start` GET → `/auth/denied?reason=not_admin` redirect、disconnect POST → 403、(b) `DISCORD_ADMIN_ROLE_IDS` を空にして dev bypass なしで login → `getCurrentUserCanEdit()` が false (= 編集ボタン非表示)、(c) `curl 'http://localhost:3000/api/page-title?url=http://169.254.169.254/'` で 400、`curl '.../api/page-title?url=http://127.0.0.1:8080/'` で 400、`/api/page-title` を 60 回連打して 429 を受領、(d) 2 ブラウザで同時に `/api/auth/fflogs/start` → cookie が別個に焼かれて互いの callback を破壊しない、(e) `curl 'https://<host>/rest/v1/app_settings?key=eq.fflogs_oauth_access_token' -H 'apikey: $ANON'` で空 (schema.sql の DELETE 実行後)、を確認。
