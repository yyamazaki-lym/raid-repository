# v2.18 (2026-10-02)

## 🔒 日付メモ: 所有者不明のメモを消せるのは admin だけに・admin が他人の名前でメモを作れないように・1 人が 1 つの日付に書けるメモを 10 件までに

### 狙い

2026-10-01 全体精査で「判断待ち」にしていた日付メモの 3 件を、2026-10-02 のユーザー決定で閉じた。

- S-10「所有者不明のメモはログイン済みメンバーなら誰でも削除できる」(L-18 で開けた) → **閉じて良い**。開けている間は、非 admin メンバー 1 人が PostgREST 直叩きで所有者不明のメモを一括削除できた
- S-11「admin が任意の作成者 ID でメモを作れる」→ **残さない**。別人のメモとして残り、監査ログも無かった
- S-3 の残り「1 人あたりの行数上限」→ **1 人 10 件**。1 人が大量に入れると全員の TOP (SSR の全件取得) と Realtime の配信が膨らむ

### 実装

- schema 7a-2: DELETE は所有者か admin だけ (`OR author_user_id IS NULL` を外した)。INSERT は本人の ID だけ (`owner_only`、admin の分岐なし)。UPDATE は変更なし
- schema 5c-2: `schedule_session_memos_enforce_limit` (BEFORE INSERT のトリガー)。**1 つの日付に 1 人 10 件** と解釈した (メモは日付ごとに付くので、全期間の通算だと練習日が増えるとすぐ書けなくなる)。作るときだけ数える (予定の日時の変更で raw_date をまとめて付け替える `update_native_placeholder_raid_times` を止めない)。所有者不明の行は数えない。同じ人・同じ日付の作成は advisory lock で 1 件ずつにして、同時の INSERT で上限を越えない。弾くときは `memo_limit_per_date`
- `memo-permissions.ts`: `canDeleteMemo` を編集と同じ規則にした。`MEMO_PER_DATE_LIMIT = 10`
- `schedule-memos-client.ts`: 上限の語を見分けて「メモは 1 つの日付に 1 人 10 件までです」(英語も) を出す
- 練習ログのミス注釈は追加の上限を入れない: タグは固定の 10 種で Server Action が一覧外を弾き、一意の索引が重複を弾くので、1 pull あたりチーム帰属 10 件・個人タグ 1 人 10 件で頭打ちになっている
- HANDOFF の保留 2 件 (Discord 通知トグル OFF の扱い / TODO #92) をユーザー決定で閉じ、節を「現在なし」に戻した。backlog の S-10 / S-11 / S-3 / F-9 に決定を書いた

### 検証

- `check-memo-permissions`: 真理値表 (所有者不明は一般メンバーには削除させない・編集と削除の可否が全組み合わせで一致)、schema (DELETE に NULL の分岐が無い・INSERT は `owner_only`・`owner_only` に is_admin が無い・トリガーの上限 = `MEMO_PER_DATE_LIMIT`・所有者不明は数えない・同じ人と日付で数える・advisory lock・INSERT だけ)、画面の語の見分け

## 🎬 練習ログ: オフセットがマイナスの動画で、録画開始より前に始まった pull の動画番号を灰色 + 取り消し線で出すように (押しても開始の場面には飛べないことが分かる)

### 狙い

2026-10-02 実機要望。オフセットがマイナスの動画 (録画開始が pull #1 より後) では、
録画開始より前に始まった pull の動画上の秒がマイナスになる。リンクは
`buildVideoTimestampUrl` で 0 秒に丸まるので、押してもその pull ではなく動画の
先頭が開く。見た目は他の番号と同じで、どの pull が動画で見られないのか分からな
かった。

### 実装

- `src/lib/video-sync.ts` に `isBeforeVideoStart(videoSeconds)` (秒が負なら映って
  いない、0 秒ちょうどは映っている) を足し、オフセット設定の「動画に最初に映る
  pull」(`explainOffset`) もこれを使うようにした。設定画面と行で境界が食い違わない
- `pull-row.tsx` は動画上の秒を `videoSecondsForPull` (逆算と対の式) で出すように
  し、映っていない番号を灰色 + 取り消し線にする (色だけに頼らない)。その pull の
  動画が全部映っていなければ、チップの枠とマークも灰色にする
- title / aria-label は専用の文言 (`videoMomentOutsideTitle`) で「録画開始の何分
  何秒前に始まったか」と「押すと動画の先頭を開く」を出す。リンクは残す (動画を
  開く手段としては使える)

### 検証

- `scripts/check-video-sync.mjs` に、境界 (-0.001 / 0 / 正)、オフセット -82 の
  実機例、7 通りのオフセットで「設定画面の最初に映る pull = 行で灰色にならない
  最初の pull」、pull 行の配線 (式の手書きの写しが無い・判定と専用文言を使う) を
  足した。境界を `<=` にする / 設定画面だけ別の境界にする / 行で判定を使わない /
  式を手書きに戻す / 専用文言を使わない、の 5 通りの変異がすべて検査で落ちる
- dev の一時ページに合成した 4 pull × 動画 2 本 (オフセット -300 / -120) を並べて
  実測した: 両方映っていない行はチップ全体が灰色、片方だけの行はその番号だけ
  灰色 + 取り消し線、0 秒ちょうどの番号は通常色。行の高さ (32.5px) とチップ幅
  (60px) は全行で同じ。一時ページはコミット前に削除した

## 🩺 自動処理: Discord 取り込みで次回へ回した URL の件数を記録に出すように (時間切れ・件数の上限で残した回は「一部 (残りは次回)」になる)

### 狙い

2026-10-01 の #408 で、Discord 取り込みに持ち時間 (220 秒) と 1 チャンネル 50 件の
上限を入れ、超えた分は次回へ回すようにした。ところが次回へ回した件数 (`deferred`)
と持ち時間切れ (`skipped: "deadline"`) は cron の応答 JSON にしか出ず、console にも
DB にも残らない。runtime logs は Hobby で 1 時間しか残らないので、01:00 JST の回で
どれだけ残したかを翌朝に確かめる手段が無かった (2026-10-02 に本番で確かめようとして
判明)。自動処理の記録 (#413) も成功 / 失敗しか持たず、残した回も「成功」になっていた。

### 実装

- `src/lib/discord-import-budget.ts` に純関数 `summarizeDiscordImportRun` を足し、
  チャンネル単位の結果から記録に載せる成否と理由を作る
  - 失敗したチャンネルが 1 つでもあれば「失敗」。理由は従来どおり最初の 1 つ
  - 失敗が無く、次回へ回した URL か持ち時間切れのチャンネルがあれば「一部」
    (`CronOutcome` の `partial` の定義「時間切れなどで一部を次回へ回した」どおり)
  - 理由は英語のコードで `deferred 12 new URL(s); 2 channel(s) stopped at the deadline`
    の形。失敗の回も末尾に件数を書き添える。何も残さなかった回は従来どおり理由なし
- `import-discord` の route は成否の組み立てをこの関数に任せる

### 検証

- `scripts/check-discord-import-budget.mjs` に境界 (空・停止中だけ・deferred 0・
  件数の合計・持ち時間切れのみ・両方・失敗 + 件数・理由なしの失敗で末尾の空白) と
  route の配線を足した。「残した回を成功にする」「失敗の回に件数を書かない」
  「route が理由を渡さない」の 3 通りの変異がすべて検査で落ちる
- `scripts/check-cron-status.mjs` (応答の直前で記録する配線) も通る
- 本番の実行で記録が変わるのは次の 01:00 JST の回から。画面の表示は既存の
  「一部 (残りは次回)」と理由の表示をそのまま使う

## 📺 動画: YouTube の再生リストを登録すると、限定公開の動画も毎晩自動で動画タブに取り込むように (コンテンツ設定で再生リストの URL を指定・メンテナンスメニューの「⑤ YouTube 再生リスト取り込み」で今すぐ実行も可)

### 狙い

2026-10-02 実機要望。「YouTube の限定公開の動画をチャンネル指定で自動取り込みしたい」。

限定公開の動画はチャンネルの動画一覧・検索・登録者のフィードに出ない (YouTube ヘルプの公開設定の表)。API キーでも RSS でも、チャンネルから見えるのは公開の動画だけなので、チャンネル指定では取れない。一方で同じ表に「公開の再生リストには表示できる」とあり、実際の再生リスト (限定公開 11 本) をキー無しで開くと 11 本とも載っていた。そこで **再生リストを指定して** 取り込む。

動画のタイトルが録画開始の時刻 (「2025 05 27 22 00 57」) で、投稿日は 11 本中 10 本が同じ日 (まとめて上げたもの) だった。既存のタイトルの日付の読み取り (`title-date.ts`) で 2025-05-27 と読めることを確かめたので、日付・Logs への結びつけは既存の経路 (タイトルの日付を優先) がそのまま使える。

### 実装

- schema: `categories.youtube_playlist_ids text[]` (上限 10、NOT VALID の CHECK) と、`category_links.source` に `'youtube'` を足した。source の CHECK は列と一緒に作られた名前の無い制約なので、`pg_constraint.conkey` で「source 列だけを参照する CHECK」を探して外し、名前を付けて足し直す (環境ごとに自動の名前が違っても置き換わる。`logs_url_source` は巻き込まない)
- `src/lib/youtube-playlist.ts` (純関数): 再生リスト ID の切り出し (別ホスト・ミックス `RD`・「後で見る」`WL`・クエリの注入を弾く)、API の応答から取り込む動画を選ぶ (非公開・削除済み・重複を外す)、既存の動画・取り込み除外との照合を **動画 ID で** 行う (Discord に `youtu.be/<id>` で入っている動画を二重に入れない)
- `src/lib/server/youtube-playlist-import.ts`: `playlistItems.list` を 50 本ずつ最大 20 ページ読み、`videos.list` で長さを取り、Discord 取り込みと同じ形で保存する (重複は skip、まとめての保存が失敗したら 1 行ずつ)。エラーの理由には API キーを含む URL を出さない
- 毎晩の cron (`/api/cron/import-discord`) で Discord 取り込みと並べて走らせ、どちらかで動画が入れば Logs 同期を 1 回起動する。実行記録 (#413) には両方の失敗を載せる
- コンテンツ設定に「YouTube 再生リスト」の欄 (1 行 1 本)。保存側 (`updateCategoryAction`) でも形と上限を検査する
- メンテナンスメニューに「⑤ YouTube 再生リスト取り込み」と結果パネル。動画カードに取り込み元の印、⋮ の「今後取り込まない」を再生リストの動画にも出す (除外で消す対象にも足した)

### 検証

- `scripts/check-youtube-playlist.mjs` (新規): ID の切り出し 16 通り、入力の正規化、取り込む動画の選び方 (実測した再生リストの ID を使った応答の例)、動画 ID での照合、配線 (schema の上限 = TS の定数、source の CHECK、保存側の検査、除外、cron の締切、エラーの理由)。変異 11 通り (ホストの検査を外す・非公開を通す・URL の文字列で照合する・schema の上限をずらす ほか) がすべて検査で落ちる
