## 仮説 1 (有力): コールドスタート + Supabase DB 接続遅延

参考記事 https://note.com/light_systems/n/n8431aa59d7f7 (Vercel + Neon の cold start で「DB 接続だけで 2-3 秒」「朝イチアクセスが 3-5 秒」)。Raid Repo は Supabase だが同様の現象が起きうる。記事の主因は「Function リージョン と DB リージョンの不一致 → 太平洋横断で RTT 数百ms × PostgreSQL TCP 8 RT = 累積遅延」。

**制約**: 全ポータルページ Edge runtime は FFLogs scrape (Cloudflare bot 判定を Edge IP ですり抜け) のため固定。Node Lambda 化は FFLogs 系ルートで 403 を誘発する。動画/カテゴリページが FFLogs に触れていないなら個別に Node runtime + リージョン固定への切替検討余地あり。

## 仮説 2: deploy 後 chunk hash mismatch / RSC payload skew (part1 で非該当判定)

1.9.x で `<Link>` 復活 + `ChunkErrorHandler` + Next.js `deploymentId` skew protection を入れた経緯あり。両者現存し機能している前提で part1 では棚上げ。再発経路 (RSC stream stuck / Suspense fallback 永久 / Service Worker / browser cache が古い chunk URL を保持 / prefetch 暴走 等) を疑う場合のみ再着手。

### 後任エンジニア向けの注意 (2026-06-11 版に更新)

- 「Server Action は呼び出し元 page の runtime で実行される」仕様自体は変わらないが、scrape の HTTP 取得は `fflogs.ts` の `fetchScrapePageHtml()` が常に Edge proxy 経由にするため、**呼び出し元ページの runtime に依存しなくなった**。FFLogs 系の新規開発で fflogs.com への fetch を追加する時は必ず同ヘルパー or scrape-proxy を経由すること (Node 直 fetch は恒常 403)
- scrape エラーの reason には経路表記がある: `(page N, edge 経由)` = proxy は機能、fflogs/Cloudflare 側の問題 / `(page N, direct)` = proxy 不達 (CRON_SECRET / VERCEL_PROJECT_PRODUCTION_URL の env 不備を疑う)
- cron (/api/cron/fflogs-sync) は元から Node runtime のため、日次 scrape は proxy 化以前は失敗していた可能性が高い。proxy 化後の初回発火観察は HANDOFF「保留オペレーション」項目 3 参照
