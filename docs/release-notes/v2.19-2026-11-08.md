# v2.19 (2026-11-08)

## ✍️ 練習ログ: ACT が使えずログが無い日の分を手動で記録できるようにした (総 pull・層ごとの pull・練習日数・ログ合計・到達度・討伐数、週のまとめ、一覧のスパークラインに入る)

### 狙い

ACT が使えなかった日は FFLogs にログを上げられず、練習ログの集計 (総 pull・層ごとの pull・ログ合計の時間・練習日数・進行トレンドなど) からその日がまるごと抜けていた。その日の分を手動で足して、集計に入るようにする。

利用者の選択:

- 記録する項目は「日の要約」 — 日付、区間 (零式は層、絶はフェーズ、分からなければ「不明」) ごとの pull 数・討伐数・最良の残 HP%、練習時間 (分)、メモ。書けるのは admin (「ログを同期」と同じ権限)
- 入れる範囲は「画面・週のまとめ・一覧」 — 練習ログの画面に加えて、Discord の週のまとめと、コンテンツ一覧のカードのスパークラインにも入れる (場所によって数が食い違わない)

### 実装

- 表 `practice_log_manual_days` (schema.sql 6b-13)。1 コンテンツ 1 日 1 行で、区間は jsonb の配列 (`encounter` / `phase` / `pulls` / `kills` / `best`)。零式の層は FFLogs の encounter ID で持つ (層の番号はログの encounter の最小から数えるので、下の層のログが後から入るとずれる)
  - RLS は 7 章の汎用ループ (読み取りはメンバー、書き込みは admin)。2026-10-30 以降の新しい表なので GRANT を明示 (authenticated に読み書き、service_role に全部、公開デモだけ anon に読み取り)
- **偽の pull を `fflogs_fights` に入れない。** 同期・同じ pull の判定・動画・注釈が FFLogs のレポートを前提にしているため。手動の記録は日単位で決まる集計にだけ足す
  - `src/lib/practice-log-manual.ts`: 型・入力の検証 (`validateManualDayInput`、client の値なので型から疑う)・DB の形との変換
  - `src/lib/fflogs-progress.ts`: `summarize` (日数・pull・討伐・到達・初クリアの日)、`pullBreakdown` (層 / フェーズの内訳と「不明」)、`progressTimeline` (手動の記録を含む日の印)、層の絞り込み (`filterManualToSegment`)
  - `src/lib/practice-log-manual-merge.ts`: チーム実績の「初討伐」「討伐 N 回」、各層の初討伐、各フェーズへの初到達に日単位で重ねる。手動の記録の日のほうが早ければその日を節目の日にし (時間は分からないので「—」、pull はその日までの合計)、ログが早ければそれより前の手動の pull を pull 数に足す
  - `src/lib/logs-weekly-summary.ts`: 週のまとめの日数・pull・ログ合計・最高到達・討伐・初突破 / 初到達 / 初討伐に足す。手動の記録だけの週も送る
  - スパークラインの SQL (`category_progress_by_day`) に手動の記録の区間を足す。pull 数は行数ではなく `n` の和で数える。形の壊れた要素は読まない (cast で落ちてスパークラインごと消えないように)
- 画面: ヘッダーの「手動で記録」(admin)、記録のダイアログ (`manual-day-dialog.tsx`)、日の行の「手動」の印と手動の記録の欄 (「直す」で編集・削除)、到達度の推移の印、総 pull の「うち手動 N」
- 保存・削除は Server Action (`practice-log-manual-actions.ts`)。admin を確かめてから書く。更新・削除は同じコンテンツの行だけ、RLS で 0 行になった削除を成功にしない
- データの書き出しの「練習ログ」に表を足した

### 検証

### 動作影響 / トレードオフ

- 手動の記録は戦闘時間・最速討伐・ノーデス・ワイプ原因・フェーズ滞在時間・プル箱には入らない (pull の時刻・戦闘時間・死亡数が無い)。日の行の「戦闘」は、手動の記録だけの日だと「—」
- ログと手動の記録が同じ日にある (ACT が途中で落ちた) 日は、練習時間をログ合計にそのまま足す (時刻が無いので重なりを除けない)
- 出席サマリーは変えていない (手動の記録には誰が来たかが無い)
- 本番・デモの DB には main への push で表が入る (schema の自動適用)。デモには seed の Section 9 で手動の記録が 2 件入り、ログの後の過去の候補日が 1 日確定になる

## 📅 練習ログ: ログが欠けている日 (スケジュールの開催日なのに、どのコンテンツにもログも手動の記録も無い日) を一覧で見られるようにした

### 狙い

練習した日なのにログが無い日を見つけられるようにする。手動の記録を足すきっかけにもなる。

利用者の選択: 「開催日でどこにもログ無し」 — スケジュールはコンテンツに紐づいていないので、「このコンテンツにログが無い開催日」にすると別のコンテンツを回した日まで欠けて見える。

### 実装

- 判定は純関数 `missingPracticeDays` (`src/lib/practice-log-manual.ts`):
  - 開催日 = 自前作成式は確定 (DECISION) で有志練習でない日 (全スケジュール。出席サマリーと同じ母数)、同期式は過去の日程から除外した日と時刻違いの重複を除いたもの
  - そのうち、どのコンテンツにもログも手動の記録も無い日。カテゴリの無いログがある日も「ログがある」とみなす
  - 範囲はこのコンテンツの最初の練習日から。後に別のコンテンツの練習があればこのコンテンツの最後の練習日まで、無ければ今日の前日まで (ティアを移った後の空き日が古いコンテンツに出続けないように)
- ログのある日は RPC `practice_log_days` (schema.sql 13c-5、コンテンツ × 日)。公開デモでは重い集計と同じく service_role だけに配り、画面はサーバーが service role で計算して 60 秒共有キャッシュに置く (スパークラインと同じ)
- 読み取り (`src/lib/server/practice-log-missing-days.ts`) は 1 年前から。読み取りに失敗したら「全部欠けている」にせずカードを出さない
- 画面: サマリーのタイルの直下に「ログが欠けている日」のカード (直近 5 日 + 残りを開く)。admin には各日に「記録する」があり、その日の手動の記録のダイアログが開く。欠けている日が無ければ何も描かない

### 検証

- `check-practice-log-manual.mjs`: 範囲 (最初の練習日から・別のコンテンツに移ったら最後の練習日まで)、どこにも無い日だけ、同じ日の 2 つの開催は 1 行、今日は除く、練習の無いコンテンツは何も出さない
- PGlite: `practice_log_days` が `fightDate` と同じ日 (session_date、無ければ開始の JST 暦日) を返し、カテゴリの無いログを NULL で返す。本番は authenticated が呼べ、デモは service_role だけ
- 手元の dev で合成データの欠けている日 6 日を実測: 5 日 + 「残り 1 日を表示」、「記録する」でその日付のダイアログが開く。375px 幅でもはみ出さない

### 動作影響 / トレードオフ

- 確定していない日 (候補のまま練習した日) は判定に入らない
- 前日の分は、毎朝の同期の前は欠けて見えることがある (カードの説明に書いた)
