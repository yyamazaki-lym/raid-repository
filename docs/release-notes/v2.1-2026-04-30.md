## 🚧 デプロイ直後遷移の無音 stuck 体感を top progress bar で改善 (TODO #54 part1)

**症状**: Vercel デプロイ直後の初回アクセス + 動画 / カテゴリページ遷移で、Server Component の Supabase fetch が cold start で数秒詰まる間、Next.js App Router 仕様上「前ページのまま静止」するためユーザーには「クリックしても何も起きない」無音 stuck に見える。何度かリロード or 遷移で warm 化すると一気に表示。

**真因の切り分け**: 仮説 2 (chunk hash mismatch / RSC payload skew) は `ChunkErrorHandler` ([src/components/portal/chunk-error-handler.tsx](src/components/portal/chunk-error-handler.tsx)) + `next.config.ts` の `deploymentId = VERCEL_GIT_COMMIT_SHA?.slice(0, 12)` が既に二重で機能していて該当しない。実体は仮説 1 (cold start + Supabase 接続遅延) + portal 配下に `loading.tsx` (Suspense fallback) が 1 つも無い構成の合わせ技で、cold start 中の遷移が完全無音になる UX 問題。1.9 系で TOP の Suspense skeleton はユーザー指示で意図的に撤去された経緯があるため、skeleton 復活ではなく「画面を fake で埋めない」打ち手を選択。

**実装**: `next-nprogress-bar` を採用し新規 client wrapper `<TopProgressBar />` ([src/components/portal/top-progress-bar.tsx](src/components/portal/top-progress-bar.tsx)) を追加、portal layout の `<ChunkErrorHandler />` 直後に配置。`<AppProgressBar height="2px" color="#06b6d4" options={{ showSpinner: false }} shallowRouting />` で上端 2px の cyan バーを描画。ライブラリが `usePathname` 変化を listen し、遷移開始 → 完了の間だけバーをアニメーション。

**意図**: cold start 自体は残るが「クリックして何かが起きている」がユーザーに即伝わり、無音 stuck の体感を直接解消する。skeleton と違いコンテンツ領域は触らないため過去の撤去判断と矛盾しない。次フェーズ (TODO #54 part2 以降) で Supabase Pooler / リージョン整合の検証へ進める段階的アプローチ。

**検証**: dev preview で起動 + login 画面までエラー無しで render。portal layout 配下のため login では描画されない (= 仕様通り)。実際の遷移アニメーションは Vercel デプロイ後に本番で確認。tsc 通過。

## 🎯 編集 iframe の per-date jump を `#row_N` URL hash anchor 方式に置換 (TODO #44 完了)

**経緯**: スケジュール TOP の確定セル / 出欠セルクリックで開く character-sheets 編集 iframe について、日付セルクリック時の「該当日付までジャンプ」処理が heuristic な translateY clipping (`280 + (upcomingIndex - 1) * 36`) で行われており、character-sheets 側の行高 (= 36px) との微妙なズレで数 px の誤差が生じていた。part7 で「URL hash anchor は honor される」ことを実証したので、heuristic を捨てて exact な hash 方式に置換する。

**実装**:

1. `parse.ts` の `ROW_RE` に capture group を追加 (`<tr id="row_(\d+)">`) し、`ScheduleSession` 型に `rowIndex: number | null` を追加。`parseSessions` が parse した行ごとに `<tr id="row_N">` の N をそのまま保存する。`null` は Discord 通知 / snapshot 由来の synthetic 行 (DOM の対応行が無い) 用。
2. `schedule-edit-frame-dialog.tsx` の prop を `targetOffsetPx?: number | null` → `targetRowIndex?: number | null` に変更。URL に `#row_${N}` (rowIndex 指定時) または `#comment` (それ以外) の hash を付与してから iframe `src` に渡す。
3. **大幅簡素化**: `SCROLL_OFFSETS` 定数 / `OffsetMode` type / `useState(offsetMode)` / `useRef(lastUrl)` reset effect / mode 循環 toggle ボタン / iframe の translateY/height inline style を全廃。iframe は `absolute inset-0 h-full w-full` でフルサイズ表示のみに。トグルボタン分の import (`ChevronsDown`/`ChevronsUp`) と `useRef`/`useState` も削除。
4. `schedule-list.tsx` の確定セル / 出欠セル click handler を `onOpenEditFrame(url, title, session.rowIndex)` に変更。`SessionRow` の `upcomingIndex` prop と `upcoming.map((s, idx) =>` の idx 引数を廃止。heuristic 計算式 `Math.max(0, 280 + (upcomingIndex - 1) * 36)` を 2 箇所削除。

**検証**: dev preview で 1) 確定セルクリック → iframe `src` の hash が `#row_0` (2026/04/30) → `#row_1` (2026/05/01) → `#row_2` (2026/05/02) ... と日付に完全連番で対応することを確認、2) iframe に inline style が無く `class="absolute inset-0 h-full w-full border-0"` でフルサイズ表示、3) dialog 内アクションボタンが「新しいタブ」「Close」のみ (mode toggle 廃止)、4) tsc 通過。

**観察**: row anchor で該当行は exact にスクロールされるが、character-sheets 側の固定 table header に anchor 行が 1 行分隠される位置関係になることがある (cross-origin で `scroll-margin-top` 注入不可)。heuristic 時代の数 px ズレは根絶済 — 行特定は確実。

**撤廃済 (再導入禁止)**: heuristic translateY による per-date jump (`280 + (upcomingIndex - 1) * 36`) — 行高変動 / character-sheets レイアウト改修で容易にズレ、目視確認も難しい。`#row_N` anchor は parser が保持する N をそのまま使うので将来 character-sheets が行を増減しても portal 側で何も変えずに追従する。

## 🎯 編集 iframe URL に `#comment` hash anchor を付けて初期スクロール位置を最適化 (TODO #53 真の完了)

**経緯**: part6 で `initialMode: mid → top` に変更したが、ユーザーから指摘「現在はページ上部から開始して、日付外でスクロールして画像のようになった」 — top mode (offset=0) では iframe ロード直後は content top の凡例表示で table 行が画面外、結局手動スクロールが必要だった。

**真因**: character-sheets の input ページは **iframe 経由で開いた時に上部要素 (デイコードナビ / 大タイトル / 上部登録ボタンセット top=145) を非表示にする** responsive 判定を持つ。Chrome 直接アクセス時の DOM 調査では上部ボタンセットが見えていたが、iframe 経由ではそれらが隠されるため top mode では「凡例から始まる短い表示」になる。

**修正**: ユーザ名 header クリック時 (= no targetOffsetPx) のみ、iframe URL に **`#comment` hash anchor を append**。`#comment` は character-sheets の「一言コメント」入力欄の id (top=433) で、ロード時に character-sheets が window.scrollY = 299 (docMax 付近) に native ジャンプ → 凡例 + table header + table 行 (~15 行) + 下端 overlay 登録ボタンが同時表示される画面状態になる (Claude in Chrome で実検証してユーザー画像と一致確認済)。

**重要発見**: 1.9.15 のコメント「URL hash hints aren't honored by character-sheets」は **誤った観察** で、実は honor されている。`#row_28` で window scroll + 内部 table-container scroll の両方が連動することを Chrome MCP 経由で実検証 (1.9.15 当時はおそらく無効な ID で試した)。これにより cross-origin SOP を回避してブラウザ native の hash navigation を活用できる新しい突破口を獲得。

**target mode (= 日程セルクリック時) は触らず**: 現状の heuristic translateY 方式 (`BASE + (upcomingIndex - 1) * ROW_HEIGHT`) を維持。将来 `#row_N` 方式に置換すれば精度向上余地あり (TODO #44 改善案として記録)。

**変更箇所**: `schedule-edit-frame-dialog.tsx` で `srcUrl` を派生 — `targetOffsetPx` 無しの時のみ `new URL(safeUrl).hash = "#comment"` で append、target mode 時は `safeUrl` をそのまま使用。iframe `src` / `key` を `srcUrl` に切り替え。translateY (offset) 構造は不変、最小差分。

**検証**: dev preview で 1) ユーザ名 click → src が `...#comment` で終わる + offset=0 (translateY 不使用) を確認、2) 日程セル click → hash 無し + offset=244 (target translateY 維持) を確認、3) close 後 scrollY 復元 (part3 fix) も継続動作を確認。

## 🪜 ダイアログを閉じた後にスクロール位置がズレる事象を防御 (TODO #53)

**症状**: スケジュール (TOP) の出欠セル / 確定セル / ユーザ名ヘッダーをクリックして character-sheets 編集 iframe ダイアログを開いてから閉じると、スクロール位置がページ頭に戻ったり、しばらく scroll が効きにくく感じられることがあった。再現は条件付きで、iframe との相互作用 / focus return / 並行 re-render (Realtime メモ更新など) と base-ui の scroll lock cleanup (setTimeout 0 + exit animation) が噛み合った時に発生していたと推測。

**修正**: `schedule-list.tsx` の `openEditFrame` 呼び出し時に `window.scrollY` を `savedScrollYRef` に保存し、`editTarget` が null に戻ったタイミングで `useEffect` から rAF を 2 段重ねて (= base-ui の `setTimeout(0)` cleanup + 100ms exit animation を待つ) scrollY をチェック。差分が 4px 超のときだけ `window.scrollTo({ top: saved, behavior: 'instant' })` で復元する。差分が小さい (= base-ui が正しく復元できている) 場合は no-op なので、二重 scroll の見た目にはならない。

**検証**: dev preview で 1) 通常ケース (open → close) では scroll イベント追加発火ゼロ。2) ダイアログ open 中に意図的に `window.scrollTo(0, 0)` で scroll を破壊した「bug シミュレーション」ケースでは close 後に元の scrollY (1200 / 1400 / 1600 など) に確実に復元される、を 3 連続で確認。

## 🛟 動画ページ 選択モードの動線改善 (フォロー: TODO #47 / #52)

**問題**: bulk 削除 / クリア時間ボタンがツールバー右側に常設されていたため、(a) 長いリストでスクロール後にボタンへ戻る必要がある、(b) 選択モード中にボタンが増えるとフィルタ・並び替えが左に詰まりレイアウトがガタつく、という動線の問題があった。また ★ トグルが server action の往復を待つため反応が鈍く感じられた。

**修正**:

1. **画面下部の floating action bar に集約**: `position: fixed; bottom: 1rem` でビューポート下部にバーを固定配置。`selectMode && selectedIds.size > 0` のときのみ表示し、「N 件選択中」ラベル + ★ 追加/解除 / クリア時間 / 削除 / × 閉じる のボタンを横並びで持つ。`pointer-events-none` の外コンテナ + `pointer-events-auto` の bar 本体でカード一覧側の操作は妨げない。これでスクロール位置に関係なく操作でき、ツールバー側のレイアウトも選択モードで不変になる。

2. **bulk お気に入り**: 選択中の動画の状態を見て、未お気に入りが 1 件でもあれば「N 件 ★ 追加」、全件お気に入り済なら「N 件 ★ 解除」を出す自動切替。Promise.all で並列発火、optimistic state で即時反映。

3. **★ トグル optimistic UI**: 各カードの星クリックで `optimisticFavorites: Map<id, bool>` に書き込み、`live` より優先表示。realtime UPDATE が同じ値で届いた時点で entry を破棄 (削除済 id も sweep)。失敗時は entry を取り下げて元の状態に戻す。`favoriteCount` / フィルタも optimistic 反映済みの派生配列を見るので一貫した表示。

## 🔍 FFLogs Logs 取り込みの 2 段階バグ修正 (TODO #45 完了)

**修正 2**: 該当の reject (`return 1`) を `return 0.5` (曖昧) に緩和。「ユーザーがその動画をそのカテゴリに登録した時点で video のコンテンツはカテゴリで確定済み」という方針で、Report が **完全に分類不能** な場合は同日マッチを許容する非対称信頼関係に。Report が **別グループに分類できる** ケースの reject (l.1240-1247) は据え置きなので、同日に LH 級と Cruiser 級の raid を両方録ったときの cross-tier クロス紐づけ防止 (1.9.13 の本来の意図) は引き続き機能する。

**事前対応 (同 TODO #45 内)**: scrape 成功時のみ session cookie を auto-delete するよう `fflogs.ts` を修正済 (7d701d2)。失敗時は cookie 保持で再試行可能。これにより 403 で cookie だけ消費される事故 (= 「貼り直しても消える」運用ループ) も解消。

## 🩹 posted_at の取得元を YouTube uploadDate 優先に反転 (TODO #22 追加対応)

ユーザー指摘: タイトルに日付が無い動画でも、`posted_at` が Discord メッセージ時刻でセットされていれば紐付きはするが、古い動画 (例: 2023 年録画) を 2026 年に Discord に貼った場合 posted_at = 2026 になり、結局 2026 年の直近セッションに誤紐付けする穴が残る。

対応: 旧設計の「Discord 時刻が真、YouTube uploadDate は NULL のときだけ補完」を反転し、**YouTube uploadDate が取得できれば常に上書き** に変更。

変更箇所:
1. `enrichVideoLinkDuration` (link form 経由の手動追加): `is("posted_at", null)` ガードを撤去、常に上書き。
2. `backfillVideoDurations` / `backfillVideoDurationsChunk` (バルクメンテナンス): in-loop の `needsPostedAt` 判定から `row.posted_at === null` を撤去。
3. メンテナンスメニューに「投稿日時を YouTube から再取得 (全動画)」項目を追加。`backfillVideoDurationsChunk({ forceRefresh: true })` を呼び、SQL の `posted_at IS NULL` フィルタを外して全 video 行を再スキャン。Discord 時刻で既に埋まっている誤値も YouTube uploadDate で全件修正できる。
4. force refresh モード時は後段の `backfillPostedAtFromDiscordChannels` を呼ばない (Discord 時刻フォールバックが趣旨に反するため)。通常モードでは「YouTube 失敗行を Discord 時刻で埋める」フォールバックとして引き続き動作。

これで Discord に古い動画リンクを貼っても、YouTube が真の uploadDate を返す限りスケジュール紐付けが正しく動く。タイトル日付なし & YouTube 取得失敗 & posted_at NULL の動画はこれまで通りスキップ (`session-video-link.ts`)。
