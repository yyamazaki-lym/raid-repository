## 🔧 PR — pg_cron 再登録を idempotent 化 (TODO #2 24h 観察 follow-up、jobid 安定化)

**経緯**: TODO #2 follow-up 24h 観察 ([PR #142](https://github.com/yyamazaki-lym/raid-repository/pull/142)) で発覚 — `supabase/schema.sql` Section 13 の `cron.unschedule(jobname) → cron.schedule(jobname, ...)` パターンが GitHub Actions の schema 自動再 deploy (PR #86) 経由で main push 毎に新規 jobid を採番していた (1 ヶ月で jobid=1→4→5→6→7→8→9→11→12→13→14→15 と 12 回切替)。観察 SQL を固定 jobid で書くと過去 firing を取りこぼす + 再 deploy 切替窓 (unschedule → schedule 間の数秒) で累計 6 hour 程度の発火欠落が発生していた (failed ではなく未発火扱い、運用影響は軽微だが観察性を損なう)。

**変更内容**:
- **編集** [supabase/schema.sql](supabase/schema.sql): Section 13 の cron 登録 DO block を、jobname 既存判定 + 初回は `cron.schedule`、既存時は `cron.alter_job(job_id, schedule, command)` で更新するパターンに置換。alter_job は jobid を維持したまま schedule/command を上書きするため、schema 再 deploy 毎の jobid 採番が止まる。c_schedule / c_command を DO block 内の constant 変数化して `cron.schedule` / `cron.alter_job` 両 path で DRY 化

**触らない範囲**: pg_cron / pg_net extension の `CREATE EXTENSION IF NOT EXISTS`、vault secret 経由の Bearer 取得ロジック、cron 発火 URL / schedule (`0 * * * *`) は無改修。Section 13b / 13c (sort_order RPC) も無改修。route 側 ([src/app/api/cron/notify-native-schedule/route.ts](src/app/api/cron/notify-native-schedule/route.ts)) / app_settings 系 / app コード全般も無改修。

**移行影響**: 本 PR merge → GitHub Actions schema 自動 deploy 1 回目で `existing_jobid IS NULL` 判定だが、現実は既登録 (現行 jobid=15) のため alter_job path を通り jobid=15 維持。それ以降の deploy も alter_job で同じ jobid を更新するため安定。過去の `cron.job_run_details` 行は historical record として残置 (cleanup 無し)。ENABLED='false'/'true' どちらでも挙動変化なし。

**検証**: schema deploy 後 (main merge 時に GitHub Actions が本番/demo へ自動 psql)、`SELECT jobid, jobname, schedule, active FROM cron.job WHERE jobname = 'notify-native-schedule-hourly';` で現行 jobid=15 が維持されること + 後続 main push 数回後も jobid が変わらないこと、を実機 SQL で確認予定。
