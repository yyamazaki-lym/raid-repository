## ✅ TODO #72 案 J — Claude 自前観察 (demo + Claude in Chrome) で真因 (rapid 連続 hover で複数 Popover 同時 close → React 19 batch race で `data-open=""` 残置) 確定、`{open && <PopoverContent>}` controlled unmount で根絶

**経緯**: TODO #72 案 T (PR #40) も本番残留継続。理論 (Explore agent 解析) と本番観察が乖離 = blind 試行のコスパ悪化。Claude が demo 環境 (`https://demo-raid-repository.vercel.app/`、本番と同一コードベース・同一 Vercel production build) に対して Claude in Chrome 経由で実機観察フェーズ実施。

**真因確定** (2026-05-07 demo 実機 DOM 観察):
- single hover → leave: 残留せず (正常 close)
- **rapid 連続 hover** (3 trigger を順次 hover/leave): **3 popover が visible 残留**、`data-open=""` + `data-closed: null` + `display: flex` + `opacity: 0.984`
- ページ内 click (outside): 全 popover が `data-open: null` + `display: none` に復帰
- → 真因: **複数 Popover の同時 `setOpen(false)` 並行発火**で React 19 production batch race が発生し、`data-open` 属性が外れない。`keepMounted` (案 T) でも `[&:not([data-open])]:hidden` (案 E) でも `data-open` が外れることを前提にしていたため両方失効。outside click は Base UI `useDismiss` が個別 Popover を確実な close path に乗せるため、ページ内 click で残留が解消する観測事実と一致。
- ユーザー報告「リロード直後 first hover → leave で白枠」は、本番では複数メンバーアイコンを順次素早く hover していく自然な行為で発火していた

**案 J の戦略**: `data-open` 属性更新に依存しない React レベルの **controlled unmount**。`{open && <PopoverContent />}` で open=false 遷移時に `<PopoverContent>` を React tree から完全に除外 → React unmount path で確実に DOM node が消える → batch race の影響を受けない構造に。

**修正**:
- [src/components/portal/comment-popover.tsx](src/components/portal/comment-popover.tsx): `<PopoverContent ...>...</PopoverContent>` を `{open && <PopoverContent ...>...</PopoverContent>}` で wrap (React 条件付き render)。案 A bootstrap click は残置 (副作用なし、予防策)
- [src/components/ui/popover.tsx](src/components/ui/popover.tsx): 案 T `<PopoverPrimitive.Portal keepMounted>` → `<PopoverPrimitive.Portal>` に戻す + 案 E `[&:not([data-open])]:hidden` も削除 (案 J で不要化)
