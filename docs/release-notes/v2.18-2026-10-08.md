# v2.18 (2026-10-08)

## 🔒 セキュリティ: 公開デモで、ログインしていない人が出席サマリーを取れる回数を 1 分 10 回までにした。手元の開発サーバーで cron がヘッダだけで動いていたのを止めた

### 狙い

2026-10-07 のセキュリティ精査の残り。公開デモでは、ログインしていない訪問者 (匿名ゲスト) も出席サマリーを取れる。1 回ごとにサーバーで DB の読み取り 5 本以上と集計 2 本が走るのに、回数の制限が無かった (返すのは集計値だけで、データの漏れは無い)。あわせて、#460 の直しの抜けを 1 つ閉じる。

### 実装

- 出席サマリーの取得 (`fetchAttendanceSummaryAction`): 匿名ゲストは IP ごとに 1 分 10 回まで (`guardExternalFetch` と同じ仕組み・同じ文言)。回数の確認は DB を読む前にする。メンバーは絞らない。画面はダイアログを開いたときに 1 回取るだけなので、普通の使い方では当たらない
- cron の `x-vercel-cron` ヘッダだけの通過: 「Vercel の preview」の判定に `NODE_ENV === "production"` を足した。`vercel env pull` で作った `.env.local` には `VERCEL_ENV="preview"` が入っていて、手元の `next dev` もヘッダだけで cron を通していた (#460 のコメントは「ローカルは Bearer 必須」としていたが、実際は通っていた)

### 検証

- dev (demo、匿名ゲストの視点): ダイアログを 12 回続けて開くと、10 回目までは表示され、11 回目から「短時間に何度も取得しています。52 秒ほど待ってから試してください」。止まった回は約 20ms で返る (DB を読む前で止まる)。dev の admin (メンバー扱い) は 12 回とも取れる
- cron の判定を、env の組み合わせごとに直接呼んで確かめた: 直す前はローカルの dev (`VERCEL_ENV=preview`・`NODE_ENV=development`) でヘッダだけで通った。直した後は 401。Vercel の preview だけがヘッダで通り、本番・Vercel 以外では従来どおり 401
- `check-security-2026-10-07.mjs` (上限の位置・値・器が他の制限と重ならない) と `check-url-safe.mjs` (cron の条件) に検査を足した

## 🔒 セキュリティ: 公開デモで、ログインしていない人への出席サマリーを 1 分間使い回すようにした (回数の上限がサーバーのインスタンスごとに数えられて緩んでいたため、DB を読むのは 1 分に 1 回まで)

### 狙い

#461 で入れた「匿名ゲストは IP ごとに 1 分 10 回」が、公開デモでは効いていなかった。続けて 13 回開いても全部取れ、15 回を並列に送っても止まったのは 1 回だけだった。デモには Upstash の環境変数が無く (手元に取り込んだデモの環境変数で確認)、回数はサーバーのインスタンスごとのメモリで数えられる。呼び出しが複数のインスタンスに散ると、上限は「10 回 × インスタンス数」まで緩む (挙動からの推測)。

### 実装

- ゲストに返す出席サマリーは全員同じ (同じ ID・admin でない) なので、インスタンスをまたいで共有される Next の Data Cache (`unstable_cache`) に 60 秒置く。IP やインスタンスに関係なく、DB を読むのは 1 分に 1 回までになる
- 集計の本体を `computeAttendanceSummary(viewer)` に切り出した。見る人によって変わるのは「admin か」と「本人の Discord ID」だけで、本体は cookie / headers を読まない (キャッシュの中で呼ぶため)
- 失敗した結果はキャッシュしない (投げて保存させず、次の呼び出しで取り直す)
- IP ごとの回数の上限はそのまま残す (関数の起動回数を抑える)。メンバーはキャッシュも上限も使わない

### 検証

- dev (demo、匿名ゲストの視点): 5 回続けて開くと、集計の本体が走るのは最初の 1 回だけ (139ms)。残り 4 回は 8〜25ms で同じ内容
- dev の admin (メンバー扱い): 3 回とも本体が走り、全員分の行が出る (ゲスト用のキャッシュは混ざらない)
- `check-security-2026-10-07.mjs` に、入口と本体の分け方・本体が cookie / headers を読まないこと・失敗を保存しないこと・キャッシュの秒数の検査を足した。それぞれを外す変異 5 件をすべて検出

## 🔒 セキュリティ: 公開デモで、ログインしていない人がデータベースの重い集計を直接呼べないようにした (コンテンツ一覧の到達度はサーバーで計算して 1 分使い回す)。ミス注釈の取得にも回数の上限を付け、認可の無い集計をサーバーの呼び出し口から外した

### 狙い

2026-10-07 のセキュリティ精査の残り 3 つ (いずれも公開デモの匿名ゲストまわりと、認可の無い Server Action)。

### 実装

- **重い集計の RPC**: `category_progress_by_day` と中で呼ぶ `fflogs_duplicate_pulls`、使っていない `practice_seconds_by_category` は、公開デモでは service_role だけに配る (本番は authenticated と service_role。schema.sql 15 章の 2 つ目のループ)。以前は anon キーで PostgREST から直接、回数の制限なく (`fflogs_duplicate_pulls(0)` なら全期間を) 集計させられた。authenticated も、部外者が Supabase Auth に直接ログインすればなれ、デモの表は全行が読めるので同じことができる。アプリが service role からしか呼ばない `fflogs_report_days`・`fflogs_report_duplicate_pulls` は、本番も含めて service_role だけにした。並び順の RPC 6 本は従来どおり
- **コンテンツ一覧の到達度 (スパークライン)**: 公開デモでは、ログインしているかに関係なく、サーバーが service role で計算し、全員同じ結果なので Data Cache に 60 秒置く (`category-progress.ts`)。失敗 (空) も置く (保存しないと DB が苦しいときほど描画のたびに集計が走る)。デモの SELECT は誰にでも全行開いているので、見える範囲は変わらない。本番のメンバーは従来どおり自分の cookie のクライアント
- **ミス注釈の取得 (`fetchPullNotesAction`)**: 匿名ゲストは IP ごとに 1 分 60 回 (pull 詳細と同じ)。出席サマリーと同じ処理を `limitDemoGuest` (external-fetch-guard.ts) にまとめた
- **認可の無い集計 3 本** (`fetchPracticeSecondsByCategory`・`fetchTimeToClearByCategory`・`fetchRecentImportCountsByCategory`): "use server" の `categories-actions.ts` から素のモジュール `category-aggregates.ts` へ移し、Server Action として登録されないようにした (ID はクライアントに出ていなかったが、知られれば誰でも POST で呼べた)。呼び出しはコンテンツ一覧の Server Component だけ
- **回数制限の器の名前**: Upstash の器の名前の頭にプロジェクトの本番 URL を入れた (`rl:<本番 URL>:<scope>`)。本番とデモで同じ Upstash の DB を使っても、同じ IP の数が混ざらない (Upstash を入れる前提の準備。入れていない間は従来どおりインスタンスごとのメモリで数える)
- **出席サマリー (#462 の続き)**: ゲスト向けのキャッシュに失敗 (`{ ok: false }`) も 60 秒置く。キャッシュ層の例外は Server Action の外へ漏らさず「出席サマリーの取得に失敗しました」で返す
- **デモのデプロイ時の表明**: deploy-database-demo.yml に、重い集計 5 本に anon / authenticated の EXECUTE が無いことを確かめる段を足した

### 検証

- PGlite で 13c-4 と 15 章を流した: デモでは重い集計 3 本と report 2 本を service_role だけが実行でき、並び順の 6 本は anon も実行できる (従来どおり)。本番は重い集計が authenticated と service_role、report 2 本が service_role だけ。デモのデプロイ時の表明は空。直す前の schema では表明が 8 件を挙げて落ちる
- dev (demo): メンバー (admin) とゲストで、コンテンツ一覧のスパークラインが同じ 2 つ出る。ゲストで練習ログの pull を開くとミス注釈が出る
